## High-level stack

- **Framework:** Next.js 16 (Turbopack) App Router · TypeScript
- **Styling:** Tailwind + shadcn/ui (Radix primitives)
- **Database:** Supabase (Postgres + Auth + Storage). **PostgREST caps every request at 1000 rows and does it SILENTLY** — no error, the response is simply short — so any `.select()` that can match more than a thousand rows needs a `.range()` loop (`const PAGE = 1000; for (let from = 0; ; from += PAGE) { … .range(from, from + PAGE - 1); if (!data || data.length < PAGE) break; }`, the shape used in `/api/admin/clients`). This is the quietest class of bug in the codebase: it looks like nothing until the table crosses the line, and then reports just start under-reporting. On 2026-09-14 five places were already over it — both client lists, `/api/orders`, the new-vs-returning split in admin analytics, and the design-lifecycle cron — and the payments page had been truncating for some time before that. A paginated loop also needs an explicit `.order()`: without one PostgREST's row order is unspecified and pages can overlap or skip. Queries bounded by a filter (`.eq('order_id', …)`) or asking only for a count (`head: true`) are not affected. Where a query is near the line but still under it, the comment above it carries the measured row count and the date it was measured, so the next reader sees a number rather than an assumption.
- **Hosting:** Vercel (team `team_Qve9hriFT9sNYnjWZolAcFXl`, project `prj_Oz13dkGF3W1JvSVToT8WvZBseBba`)
- **Payments:** Monobank (UA + international dual-account routing via `bank_accounts.region`; charge always in UAH, EUR shown via buffered NBU rate)
- **Email:** Brevo
- **AI:** Anthropic SDK (chatbot, generation tasks)
- **Drag/drop:** dnd-kit
- **Canvas / image editing:** Fabric.js, html2canvas, jspdf

## Editor architecture (the big one)

The photobook/travel book editor is the most complex part of the codebase. **80% of "I can't find why this is broken" debugging happens here.** Read this section before touching it.

### Core files
- **`components/BookLayoutEditor.tsx`** — the main editor (6175 lines). State, layout, photo placement, text, frames, stickers, navigation, save/preview/order. This file is the editor.
- **`components/CoverEditor.tsx`** — separate cover editor, called by BookLayoutEditor for the cover spread.
- **`components/FramesLayer.tsx`** — overlay layer for PNG + SVG frames on a page.
- **`components/FreeSlotLayer.tsx`** — non-template free-floating photo slots with their own DPI checks.
- **`components/BookPreviewModal.tsx`** — preview of the finished book. Renders backgrounds, photo slots, frames (PNG+SVG), shapes, stickers, QR overlays, and the kalka page. Multi-slot layout rendering is still pending — it currently uses single-slot getSlotDefs only.

### Supporting files in `lib/editor/`
- **`types.ts`** — `PhotoData`, `BookConfig`, `CoverState`, `CoverDecoType`, `LayoutType`, `SlotData`, `TextBlock`, `Page`. **This is now genuinely the source of truth** and the editor imports from it. Until 2026-08-31 it only claimed to be: nothing imported it, and every one of these shapes was ALSO declared privately inside `BookLayoutEditor.tsx` (and two of them a third time in `BookPreviewModal.tsx`). The copies here had drifted far behind — `PhotoData` 5 fields against the real 13, `SlotData` 5 against 11, `LayoutType` a bare `string` against a ~200-member union — so anyone who followed this doc was coding against shapes that had not been accurate for a long time. Change a shape here; do not re-declare it in a component.
- **`constants.ts`** — 98 fonts (`FONT_GROUPS`, `FONT_DATA` with `cyr` flag), `GOOGLE_FONTS_URL`, decoration variants (acryl, photovstavka, flex, metal, gravira), leatherette/fabric/velour colours
- **`page-templates.ts`** — 64 spread layouts (`PAGE_TEMPLATES`)
- **`cover-templates.ts`** — 30+ cover presets, filterable by `tags` (`photobook` / `magazine` / `journal` / `travelbook` / `wishbook`)
- **`slot-defs.ts`** — slot geometry definitions for each layout
- **`auto-build.ts`** — automatic spread building from a photo set
- **`pricing.ts`** — dynamic price calculation: base + cover + size + pages + decorations + kalka + endpaper

### Editor sub-components in `components/editor/`
- **`FontPicker.tsx`** — visual font picker with previews. **Note:** the `kalka` (acid paper) flow still uses a basic `<select>` with 10 fonts — replacing it is a known TODO.
- **`CoverTemplatesPicker.tsx`** — filtered by `productType`
- **`PageTemplatesPicker.tsx`** — spread layout picker
- **`AutoBuildModal.tsx`** — guides the user through auto-build
- **`PhotoPanel.tsx`, `PhotoEditingPanel.tsx`** — photo upload, crop, zoom inside slot
- **`TextPropertiesPanel.tsx`** — text styling
- **`TemplatePanel.tsx`, `EditorSidebar.tsx`, `EditorToolbar.tsx`, `EditorTopBar.tsx`** — UI shells
- **`SpreadNavigation.tsx`** — page-by-page navigation
- **`PreviewModal.tsx`** — local-scope preview (different from the BookPreviewModal at component root)

### Cover text model (front + back)

The cover has two surfaces — front and back — and both can carry free-positioned text:

- **`coverState.printedTextBlocks`** — front-cover text on printed covers (magazine / journal / photobook printed / travelbook / wishbook / scrapbook / graduation). Rendered by `CoverEditor`.
- **`coverState.extraTexts`** — front-cover text on soft covers (велюр / тканина / шкірзамінник albums). One-shot inscription priced at +180 ₴ via `inscriptionMethod` (`flex` or `graviruvannya`). Rendered by `CoverEditor`.
- **`coverState.backCoverTexts`** — back-cover text on printed covers. Same shape as `printedTextBlocks` (`{id,text,x,y,fontSize,fontFamily,color,bold}`, percent-positioned). Rendered by `CoverView` directly (the back cover lives in `CoverView`, not in `CoverEditor`). Free, no surcharge. Not supported on soft covers — the front-cover `extraTexts` flow already covers that audience.

All three lists are serialised in `coverState` and persisted automatically via `cover_data` on `projects` (so saved sessions, the cart payload, and the "Замовити повторно" replay flow get them for free). The cart `options` map surfaces back-cover text as `'Текст на задній обкладинці'` when present so production sees the exact strings the customer placed.

The editor's "Текст" tab on `currentIdx === 0` shows two buttons for printed covers: one for the front and one for the back. Both desktop and mobile have the pair.

### Product types the editor handles
The editor switches behaviour based on slug:
- `photobook` (photo book — default)
- `travelbook` (travel book)
- `magazine` / `journal` / `zhurnal` (glossy magazine — different cover templates, different fonts)
- `wishbook` (wishbook — cover-only, simplified UI, hides spread navigation)

The product-type detection is in BookLayoutEditor via `_slug.includes('...')` checks.

### Known editor pain points (debug-time savers)
- **Antigravity sometimes pushes broken `useT()` placement.** Run `npx tsc --noEmit | grep error TS | grep -v TS2307` after pulling. The `TS2307` filter is intentional — it ignores module-not-found errors that are not relevant.
- **i18n in DB-driven content** (Footer, products, categories) requires the `getLocalized()` helper. Footer still uses raw fields in some places — this is a known incomplete task.
- **Frames are currently overlays only.** They render on top of photos but the photo isn't constrained to the transparent area of the frame. Making frames into actual photo slots (PNG-on-top, photo underneath in transparent zone, with crop/zoom inside the frame) is the biggest open editor task.
- **`BookPreviewModal` does not yet support:** multi-slot layouts (uses single-slot getSlotDefs), crop/zoom inside slots (photos render with objectFit:cover only). Frames, shapes, stickers, QR overlays, and cover stickers ARE rendered.
- **`SpreadNavigation` keyboard arrow keys** sometimes conflict with text-editing inside slots — this is by design (focus check), but it can confuse first-time editors.

### Overlay z-order (unified layer stack)

All four overlay types — text blocks, shapes, stickers, QR codes — share a single z-order namespace per page via an optional `zOrder?: number` field on each object. This lets the user freely interleave them: text under a coloured rectangle, sticker above a frame, etc. Rendering uses `zIndexFor(obj.zOrder)` from `lib/editor/zOrder.ts`, which returns `Z_OVERLAY_BASE (100) + (zOrder ?? 0)` — putting the whole overlay stack above photo slots (zIndex 2) and below editor chrome (zIndex 50+).

When the user selects an overlay (click/tap), a small floating `ZOrderToolbar` (`components/editor/ZOrderToolbar.tsx`) appears with four buttons: send to back / send backward / bring forward / bring to front. The toolbar is rendered as a sibling inside the overlay's wrapper, so it sticks above the selected element. Handlers funnel through `zOrderAction(kind, id, pageIdx, action)` in `BookLayoutEditor`, which dispatches to the right slice of state (pages.textBlocks, pageShapes, pageStickers, qrOverlays). All four mutations push history before applying so undo works.

When a new overlay is created (`addShape`, new text, new sticker, new QR), it gets `zOrder: nextOverlayZ(pageIdx)`, which is `max(zOrder) + 1` across ALL overlay types on that page — so newly-placed objects always land on top of the current stack.

`zOrder` is intentionally optional (`?: number`) so saved projects from before this feature continue to render. Undefined is treated as 0 everywhere — old objects appear at the bottom of the new layer system and the user can re-stack them via the toolbar.

Cover overlays (pageIdx === 0) don't have the z-order toolbar yet — covers are simpler decoration surfaces and there hasn't been demand. The infrastructure is type-compatible (Shape/sticker types include zOrder), so adding it is a small follow-up if needed.

## Print render pipeline (added 2026-08-06)

Production files are made by the **Railway render service** (`render-service/`, headless Chromium + sharp), which screenshots the app's `/print/[projectId]` page (a clean, chrome-free render via `BookPreviewModal` in print mode — no trim guides, page digits, «ЗАДНЯ» labels or fake spine bands) at 300 DPI. Key facts:

- **Output shape:** travel books & magazines export page-by-page, named `01.jpg…NN.jpg` per the print partner's checker; soft-cover magazines also split the cover into `00_cover_back/front.jpg`; hard covers stay one wrap sheet (`00_cover.jpg`); photobooks export 2-page spreads (`NN_spread.jpg`). Empty forzats (forzats-as-extra-pages model, no content) are skipped and pages renumbered.
- **Travel book page geometry:** sold as «20×30» but printed on **210×297 mm** pages (partner's hard requirement) — size key `travelbook` everywhere (editor proportions, `lib/print/geometry.ts`, render service). It is NOT the photobook `20x30` (200×300).
- **A spread is TWO WHOLE PAGES, never one double-width sheet.** `mmToPx` rounds, and the two forms disagree: `mmToPx(2 × 210) = 4961` (odd, cannot halve) versus `2 × mmToPx(210) = 4960`. The service derives the spread from `pagePxW = mmToPx(page.w)`, so both halves come out at exactly one page. Measuring the spread on its own gave halves of 2480 and 2481 px, and 2481 px is 210.06 mm — the partner's checker measures to one decimal and rejected every second page («ширина 210.1 і не є рівна 210»), failing whole travel book and hard-journal uploads. 30×30 had the same latent defect (300.0 / 300.1). The `?w=` the service passes to `/print` is that same per-page width, so the capture is never resampled either.
- **Storage layout:** `guest/pb-…/print/` for order-time uploads, `drafts/<uid>/<projectId>/print/` for draft-based projects. The folder is ALWAYS unique per project — a shared `drafts/<uid>/print` folder once let one order's re-render overwrite another's cover.
- **Registration is triple-redundant:** (1) `render-order` awaits the render and registers `order_files` rows — dies on big books (maxDuration); (2) the service POSTs a completion callback to `/api/print/render-complete` with the uploaded paths; (3) the hourly `reconcile-print-files` cron lists each recent order project's print folder and registers anything missing. All three go through `lib/print/register-export-files.ts` and are idempotent.
- **Stale-deploy detection:** the service's `/health` and its completion callback report `RAILWAY_GIT_COMMIT_SHA` — check it against origin/main before debugging «фікс не працює».
- **Photo readiness:** before each screenshot the service waits for every `<img>` to load AND `decode()` (bounded 45s/photo) — a streaming JPEG at screenshot time produced distorted photos with blank bands.
- **Trim guides for human review:** the admin order page's «Переглянути макет» opens `/print?guides=1`, which overlays per-product cut lines on every content spread — cut frame at the visible edge, a gutter cut line only for page-split products (travel/journals), and a per-product safety zone (`photobook_sizes` margins, min 3 mm) — plus a Ukrainian legend. Guide math lives in `lib/print/trim-guides.ts` (pure, tested in `tests/trim-guides.test.ts`) on top of `deriveGeometry`. Guides are IGNORED whenever `?w` is present, so the render service's screenshots can never carry them. The cover gets its own guides too: in guides mode /print renders it in the PRINT SHEET's proportion (same printPageW/printPageH/printCoverMm path the render service uses, just at screen width) and overlays the cut frame plus an orange fold line — `COVER_FOLD_MM` in trim-guides.ts mirrors the editor's `COVER_BLEED_MARGINS` (partner spec, May 2026); change one → change both, the tests pin the admin side.

## Telegram Business monitoring (added 2026-08-10)

Diana's personal Telegram dialogs with clients are monitored by the public bot (Софія) through **Telegram Business** (requires Telegram Premium on her account; connected in Settings → Telegram Business → Chatbots). No group chats, no bot visible to clients.

- **Webhook:** the existing `/api/chatbot/telegram` route also handles `business_connection` (stores connection state in `settings('telegram_business_connection')`) and `business_message`. Diana's outgoing replies are recorded as `human_manager`, client messages as `customer` — everything lands in the same `social_conversations` / `social_messages` tables as Instagram, so `admin/social-inbox` shows all channels.
- **Modes** (`settings('telegram_business_mode')`): `draft` (default — AI reply is sent to Diana as a suggestion in her chat with the bot, never to the client), `auto` (bot answers the client on behalf of her account via `business_connection_id`; requires the "reply" permission, degrades to draft without it), `off` (record only). Flipping the mode is a settings row update, no deploy.
- **Human-is-in-charge rule:** after Diana replies manually in a dialog, the bot stays silent there for `settings('telegram_business_human_silence_hours')` (default 3).
- **Watchdog cron:** `/api/cron/social-unanswered` (every 30 min, 08:00–22:30 Kyiv) alerts in Telegram about dialogs where the last message is from a customer older than `settings('social_unanswered_hours')` (default 3h) and about `needs_human` escalations. Muted on purpose: dialogs with status `human_handling`, and dialogs a manager replied to within `settings('social_watchdog_active_hours')` (default 24h — the "it's in someone's folder" equivalent, since bots can't see Telegram folders). A dialog re-alerts only every `settings('social_watchdog_realert_hours')` (default 3h; state in `settings('social_watchdog_alerted')`). `?preview=1` returns the payload without sending. **The alert names the dialog and how long it has waited, and never quotes the message** (2026-09-14): `text` was removed from the `WaitingDialog` type itself, not just from the print sites, so a quote cannot come back without editing that type. The same cron also refreshes the conversation→order link (`link_social_conversations` RPC, skipped under `?preview=1`) — that is what keeps Софія seeing dialogs created since the last run.
- **Webhook registration is self-healing:** `/api/cron/telegram-webhook-sync` (every 15 min) compares getWebhookInfo against the desired URL + `allowed_updates` (incl. `business_*`) and re-registers on drift — a fresh bot token starts working within one tick, no manual step. `POST /api/chatbot/telegram/setup` (admin-only) remains as the immediate manual trigger. Helpers live in `lib/chatbot/telegram-business.ts`.
- **What leaves the inbox** (narrowed 2026-09-14, both paths). The watchdog and `/unanswered` used to quote 120 characters of the client's last message into the work chat; they now print only who is waiting and for how long. `lib/chatbot/client-chat-lookup.ts` used to search every message for a phone and then for a name, and fed up to 40 messages of whatever it found to the Anthropic API; it now reads only the dialog whose `order_id` matches, ignores links of confidence `name` entirely, and sends 15 messages. When no dialog is linked it returns `NO_DIALOG_LINE` — an explicit sentence, never an empty string, because a hole in the facts is exactly where the model invents (the same fix as the `клієнт НЕ лишив email` line). Access to the inbox itself is NOT the RLS policy (`is_admin_user()`, 4 emails) — the route reads with the service key behind `requireSection('ai','view')`, so every active staff member can read any dialog; narrowing that is a role-level decision (`ai: none`), not a code change.
- **Work group chats** (`lib/chatbot/work-commands.ts`): the bot in a group (or Diana's own private chat with it) is a control panel, never the customer AI. Registration is owner-gated (`/register`, owner = the Telegram Business account); after that any member can use `/status` (24h summary), `/order TM-…`, `/overdue`, `/unanswered`, `/chatid`. `/alerts_here` points team alerts at that group (settings `telegram_alerts_chat_id`; registered chats in `telegram_work_chat_ids`). The unanswered computation is shared between the cron and the command via `lib/chatbot/unanswered.ts`.
- **Софія cannot state an order fact without holding the order row** (2026-09-14, after a live failure). The router's last resort is `chatAboutLife`, a separate model call at temperature 0.8 that sees only recent chat lines and no order data. A question about TM-001314 whose number failed to parse landed there and produced an invented status, an invented deadline («15 січня» against a real 15.09) and an invented «склад укомплектований». The prompt already said «нічого не вигадуй про замовлення» and that did not hold, so the guard is now structural: `workGuardReply()` returns the order-number clarifier for anything matching `WORK_TOPIC` (замовлення/дедлайн/оплата/статус/склад/накладна/ТТН/номер) or anything number-shaped, in the message OR in the message it replies to, and it is checked both in the router and at the top of `chatAboutLife` — so no path reaches the model with a work topic. Small talk still works.
- **Order numbers are read in Cyrillic and in shorthand** (`extractOrderNumbers`, same date). «Тм-001314» typed with Cyrillic Т and м was invisible, and so was the team's «1314» — the old regexes took Latin prefixes only and a bare number of exactly five digits, always mapped to CRM. Now a homoglyph-normalised copy feeds the prefix match (Cyrillic Т/М/С/Р/В → Latin; «СРМ» normalises to CPM, which is accepted as CRM), and short forms — 4-digit «1314» and «001314» → `TM-001314` — are available per caller via `{ allowShortForms }`, requiring an order word within 30 characters before the number, or `{ assumeOrderContext }` when the message is a reply to Софія. They stay OFF for the silent mention capture, where four digits are usually a page count. Prices are still excluded by the currency check on the tail.
- **The reconcile queue is oldest-snapshot-first** (`orders.crm_reconciled_at`, 2026-09-14). `findSyncedOrders` used to order by `created_at desc` and take 25, so the same 25 newest orders were re-read every 30 minutes and everything below rank 25 was never reconciled again: of 131 site orders holding a CRM snapshot, 81 were older than a week and 16 older than a month, and 33 adopted cards had never been reconciled at all (they carry `payments_total`, written at adoption, but no `manager_name`, which only the reconcile writes). The queue now orders by `crm_reconciled_at asc nulls first, created_at desc`; the batch stays 25, so a full sweep takes about six runs (~3 hours) and load on KeyCRM is unchanged. The stamp is written on every successful pass — including when nothing changed, which is the fact that was missing — and also when the CRM answers that the card no longer exists, but NOT after a failed request, so a broken order stays at the head of the queue instead of silently rotating to the back. Orders in an active state (`ACTIVE_BEYOND_WINDOW`: new, confirmed, in_production, quality_check, ready, shipped) are now taken regardless of the 45-day window — three live orders were older than that and would never have been reconciled — while the window still keeps hundreds of finished cards out.
- **The KeyCRM stage is translated on DISPLAY, never in the mirror** (`lib/automation/crm-stage.ts`, 2026-09-14). KeyCRM returns its own built-in statuses under their internal keys and the team's own pipeline stages under their Ukrainian names — one map, two vocabularies — so 597 of 1011 cards showed the manager `completed` / `in_transit` / `waiting_for_prepayment`. `crmStageLabel(stage, siteLabel)` translates the five known keys, passes a Cyrillic name through untouched, and for an unknown key shows the site status with the key in brackets («підтверджене (CRM: returned)») plus a one-time console warning. It returns null when there is no stage at all, because 96 orders never reached the CRM and «Етап у KeyCRM: підтверджене» would be an invention; `stageOrStatus()` is the list-line variant that falls back to the site status. `custom_attributes.keycrm.status_label` still stores exactly what the CRM sent, and `status_id` is now stored beside it so a renamed stage cannot break the translation. **The four substring matchers stay as they are** — `statusFromCrm`, `isClosedCrmStage`, `fulfilmentFromLabel` and the risk-radar regex answer «what does this mean for the work», understand both vocabularies on purpose, and must not be routed through the dictionary. `SITE_STATUS_UA` also lives in that module now: it used to be two identical copies in work-questions.ts and work-commands.ts (the production-calendar page keeps its own capitalised labels deliberately).
- **Work-chat order mentions** (`lib/chatbot/work-chat-monitor.ts`): non-command group messages mentioning an order (TM-…/CRM-…/bare 5-digit KeyCRM id; numbers followed by грн/₴ are prices and skipped) are captured silently — an `order_history` note (`work_chat_note`/`work_chat_done`) + deadline TIGHTENED to any dd.MM date (earlier-only; completion reports never tighten). Completion attribution ladder: number in the message → number in the replied-to message → (done-reports only) the chat's last direct mention within 2h. Orders not yet mirrored from KeyCRM wait in `settings('work_chat_pending_mentions')` (48h TTL), drained every 15 min by the telegram-webhook-sync cron. Reactions: ✍ instruction / 👌 done — never a chat message. Needs the bot as group admin to see non-command messages.
- **Proactive team alerts** (all to the `/alerts_here` destination, falling back to Diana's chat with the bot): 💰 paid-order ping fired from the Monobank webhook on the first transition to paid (test orders excluded via `lib/automation/test-orders.ts`); ☀️ morning digest `/api/cron/work-chat-digest` (06:00 UTC) = deadlines only per Diana's 2026-08-11 format — overdue + due within `settings('digest_upcoming_days')` (default 3) + one dialogs line; 🌙 evening sign-off `/api/cron/work-chat-evening` (19:00 UTC) with the unanswered count and солодких снів; 🔔 unanswered-dialogs watchdog (see above). Bot personality: first data command per chat per Kyiv day gets a time-of-day greeting (ранні пташки < 8:00, соньки > 10:00 — `morningGreeting()` in work-commands.ts).

## Pricing flow

Photobook prices are NOT hardcoded in the codebase. They live in Supabase, in the `photobook_prices` table (joined to `cover_types` and `photobook_sizes`). Three components work together:

1. **`app/api/pricing/photobook/route.ts`** — GET endpoint, server-side. Reads the full matrix (~466 rows) from Supabase, flattens it into a `{ cover_type, size, page_count, base_price, kalka_surcharge }` shape, returns JSON. Uses Next.js `revalidate = 60`, so price changes propagate to prod within 60s of a migration without redeploy.

2. **`lib/editor/usePrices.ts`** — client React hook (`usePhotobookPrices`). On mount, seeds state from `localStorage` (24h TTL) for instant first paint, then fetches `/api/pricing/photobook` in the background and updates state if anything changed. Returns `{ table, loading, error }`. Used by `BookLayoutEditor`, `EditorTopBar`, and the photobook product page.

3. **`lib/editor/pricing.ts`** — pure module. All exported functions (`lookupPrice`, `lookupPriceWithKalka`, `findPriceRow`, `calculateDynamicPrice`) take a `PriceTable` (or `null` for the fallback path) as their first argument. Knows nothing about React, fetch, or Supabase. Handles cover-type aliasing (`Velour` / `велюр` / `Velvet` → canonical `Велюр`), size normalisation (`20x30` → `20×30`), nearest-page-count fallback, and graceful null-table fallback to the price the user already saw.

**Why this shape:** the editor route uses `dynamic: 'force-dynamic'` + `ssr: false` (the editor needs browser APIs and is 200KB+), so a Server Component cannot pass prices in as a prop. Going through a thin API route lets us keep server-side caching while still letting the client refresh on its own schedule.

**Tracing paper ("калька") on the product page is not added to the displayed price** — the radio is intentionally lead-gen ("ціна уточнюється"). The editor, where kalka is part of the live config, does add the `kalka_surcharge` from the DB.

### Page-priced products (журнали + Travel Book) — and the drift check

Photobooks are priced from one table (`photobook_prices`) and have no second copy. The **page-priced** products do, and that is where price bugs keep coming from:

| Half | Where | Who prices from it |
|---|---|---|
| The scale — absolute ₴ per page count | `lib/products.ts` (`PHOTO_JOURNAL_SOFT`, `PHOTO_JOURNAL_HARD`, `TRAVEL_BOOK`) | конструктор (`BookConstructorConfig`), картка товару через `getCalculatedPrice` |
| База + надбавка за опцію | `products.price` + `products.options['Кількість сторінок'][].price` | сторінка товару (`ProductClient` Source 2/3) |

The two agree **only while `products.price` equals the cheapest tier of the scale.** Nothing enforced that, and on 2026-08 the hard-cover journal gained a 12-сторінковий tier at 675 ₴ while the column stayed at its old 825 ₴ — every configuration of that product went out exactly 150 ₴ over until TM-001202 was paid at 825 ₴ instead of 675 ₴.

**Migration to a single source is underway** (started 2026-08-19). `page_product_prices` (Supabase) holds the same 87 tiers as absolute prices — one row = slug × page_count × ₴, seeded by script from `lib/products.ts`, mirrored to the hryvnia at creation (SQL cross-check: 0 mismatches). `GET /api/pricing/page-products` serves it with the same 60s-revalidate contract as the photobook route. **Reads are NOT switched yet** — the site still prices from the old pair, while the audit now compares all THREE copies twice a day in the ops digest (`tableDrift` / `tableMissing` / `tableExtra` in the report). Switching reads (product page, selector, constructor, catalog cards) is the next step, only after several days of clean three-way audit.

Two things now hold it together:

- **`lib/pricing/audit.ts`** — pure; recomputes both halves for every tier of every page-priced product and reports each hryvnia of disagreement. When all tiers are off by the same amount it names the correct база, so the report is an instruction and not a list of symptoms. Read it from `GET /api/admin/pricing/audit` (staff-only) after any price change, and it runs inside the twice-daily **ops digest**, where drift is pinned above every order bucket.
- **`ProductClient`** derives `dynamicPrice` for journals from the scale on every options change (Travel Book already did). `products.price` is a display fallback, not the charged price.

- **`lib/pricing/final-price.ts`** — `computeFinalPrice()`: the product page's final price + labeled breakdown, extracted verbatim from `ProductClient` (2026-08-19) where it was ~150 untestable inline lines. Three sources by priority (photobook table → dynamicPrice → DB option modifiers), then percentage rush BEFORE flat extras. `getCalculatedPrice` and the inscription key are passed in / duplicated because their homes are `'use client'` modules — a test pins the key against `INSCRIPTION_KEYS.on`. `ProductClient` is now a thin caller; do NOT grow pricing arithmetic inside the component again.
- **`tests/pricing-*.test.ts` + `tests/final-price.test.ts`** — the only tests in the repo (Vitest, `npm test`, about one second). They pin every tier of every page-priced product as a literal, the order in which the rush multiplier and the flat extras are applied, the option predicates that read rush and lamination out of values/labels/locales, and the audit itself. Both halves are covered on purpose: `pricing-scales` is the price list written down, `pricing-composition` is what happens when the customer also picks rush, lamination and typesetting — the layer where every historical bug actually lived. Verified by mutation: reverting the string-page-count fix fails 6 tests, moving one tariff by 5 ₴ fails 3.

**Adding a product to the audit:** append it to `PAGE_PRICED_PRODUCTS` in `lib/pricing/audit.ts` with its scale from `lib/products.ts`. Do NOT add photobooks — they have no second copy to drift from, and a hardcoded photobook table here would recreate the bug the audit exists to catch.

**Known gap:** the hard journal is sold in 4-page steps (12, 16, 20…) while its twin Travel Book is sold in 2-page steps (12, 14, 16…) off the identical 75 ₴ scale. A hard journal built to 14 pages in the editor rounds up to the 16-page price — the same "paid for 24, received 22" class as TM-001195. Filling in the odd tiers is a product decision for Diana, not a code fix.

**Historical note:** Until 2026-05-14, `pricing.ts` shipped a hardcoded ~150-row table. The table drifted from the DB — `velour_20×30` was missing entirely, so the editor showed 1200₴ instead of 1985₴ for velour 20×30 / 10pp / +kalka. The hardcoded table has been removed; the DB is now the single source of truth.

## Payment flow & designer handoff

The end-to-end path from cart to designer brief:

1. **Cart → checkout.** The `/cart` page is now **navigation-only** — it lists items and totals and its button routes to `/[locale]/checkout`. It no longer collects contact/delivery or creates orders (the old `/cart` "Pay" button POSTed to a deleted `/api/checkout/create-invoice` and 404'd, blocking all online payment). `/checkout` is the single online entry point: it owns the contact → shipping → payment steps, calls `/api/orders/submit` (which resolves `payment_mode` and may downgrade split→full), then `/api/monobank/create-invoice`. It also runs `linkPendingExports` — reading each `sessionStorage.export_{cartItemId}` descriptor that constructors stash and inserting `order_files` rows — **before** `clearCart()`, so designed files (photobook PDFs, posters, star maps) always attach to the order. `lib/submitOrder.ts` inserts the `orders` row with `payment_status='pending'`, `order_status='new'`; line items go into `orders.items` JSONB.

2. **Invoice creation.** Customer hits "Pay" → POST `/api/monobank/create-invoice` with `{orderId, paymentRegion: 'ua'|'international'}`. The token is now taken from the active `bank_accounts` row whose `region` matches the destination (UA → ФОП Коблик, international → ФОП Гоголь); env tokens (`MONOBANK_TOKEN` / `MONOBANK_TOKEN_INTL`) are only a fallback if the DB row is missing. The charged amount is `order.total` (already the marked-up UAH — see "Region pricing" below), or `prepaid_amount` for a 50/50 split. Stores `monobank_invoice_id` + `monobank_payment_url`, logs to `order_history`, returns the page URL. Always charges in UAH (`ccy: 980`); foreign cards are converted by the customer's own bank.

3. **Customer pays on Monobank.** Monobank fires a webhook to `/api/monobank/webhook` (canonical path). Two legacy aliases — `/api/webhook/monobank` and `/api/webhooks/monobank` — re-export the canonical handler, so Monobank can hit any of the three URLs without breaking.

4. **Webhook handler** (`app/api/monobank/webhook/route.ts`) does, in order:
   - Verify the `X-Sign` signature with `MONOBANK_PUB_KEY`. Production webhooks without a configured pub key return 503 to avoid silently accepting unsigned payloads.
   - Look up the order, sanity-check that `amount` matches `total * 100` ± 1 kopeck (defence in depth).
   - Atomic conditional UPDATE on `orders` setting `payment_status`, `monobank_invoice_status` etc, through the `apply_monobank_payment()` SQL function (a direct PostgREST update breaks whenever the schema cache goes stale on `monobank_invoice_id`). It writes only when the (invoice id, invoice status) tuple is new, and returns the order id only to the caller that won that race — concurrent deliveries can't both insert duplicate history rows.
   - **Stage order: a later state is never overwritten by an earlier one (2026-09-14).** Monobank does not guarantee delivery order, and "the tuple is new" said nothing about *direction*: on TM-001087 a `processing` event landed 47 ms after `success`, differed from it, passed the guard, and wrote `payment_status` back to `pending` — a paid order reading unpaid, with the money-red badge and a place in «Потребує уваги». `paid_at` survived only because it alone was written conditionally, which is what made the damage visible. The race hit 7 orders; 4 still carried a stale stage and 1 a stale payment status when this was fixed. `mono_stage_rank()` now ranks the lifecycle — `created` 10, `processing` 20, `hold` 30, `expired`/`failure` 35, `success` 40, `reversed` 50, anything unknown or NULL 0 — and the UPDATE's WHERE applies an event only if its rank is not lower than the stored stage's. Two things about that table are load-bearing. `reversed` sits ABOVE `success` because a refund legitimately follows a payment and must apply. `failure` and `expired` sit BELOW `success` rather than beside it: on equal ranks a `failure` arriving after `success` would pass a "not lower" test and mark a paid order failed — the same defect mirrored — so on top of the ranks there is an explicit rule that **once the stored stage is `success`, nothing applies except `reversed`**. A DIFFERENT invoice id skips the rank check entirely and is its own branch of the WHERE: a re-issued payment link starts at `created` (rank 10) and comparing that against the old invoice's `success` would reject every event of the new attempt. Migration `20260914_monobank_stage_order.sql`, which also repaired the four historical rows (the amount on TM-001087 is a reconstruction — see the migration header for what each value rests on). The rule lives only in SQL and has no vitest twin on purpose: a TS copy would be the drift risk, not the safety net — exactly how the two copies of the paid-in-full rule drifted apart and had to be stitched back together by a test. It is tested where it lives instead, by `supabase/tests/monobank_stage_order.test.sql`: a read-only `do $$ … $$` block that raises on the first mismatch, covering the rank ORDER (not the literal numbers, so the gaps stay re-spaceable) plus every lifecycle transition worth asserting. Run it in the Supabase SQL editor or via `psql`; it touches no tables and is safe on production. `npm test` does NOT run it — vitest cannot see Supabase — so run it by hand after any change to either function. **Anything that confirms a payment must also write the stage it is confirming**, or it disarms that guard on exactly the orders it just fixed: an order left at `created` (rank 10) accepts a late `failure` (rank 35) and flips a paid order to failed. `check-payment` writes the stage it read from the bank (`ff3d379f`); `mark-paid` writes `success` **only when the order carries a `monobank_invoice_id`** (`20260914_mark_paid_invoice_stage`) — that button is also used for money that never went through Monobank at all (cash, transfer, COD), and stamping a bank-invoice stage on those would be inventing an event that never happened.
   - **Claim the paid transition (2026-09-13).** `paid_at` is NOT set by that function any more (`p_set_paid_at` is always false). Instead, on `success` the handler runs one guarded UPDATE — `set paid_at = now() where id = ? and paid_at is null` — and EVERY once-per-order side effect below hangs on whether it returned a row. Before this they all asked `existingOrder.payment_status !== 'paid'`, a snapshot read at the top of the request: stale by the time it was used, so a manual «Позначити оплаченим» landing in between, or a second webhook for the same invoice with a different status, made two callers each decide they were the first and each send the paid email. The condition now lives in the UPDATE's WHERE, where only one caller can win it. The side effects are: stock deduction, the paid email, the work-chat ping, referral reward, agency commission, certificate redemption, babybook start, production automation, fiscalisation, print render, designer handoff, certificate issue.
   - Insert into `order_history` with the human-readable note.
   - On `success`: auto-confirm the order if it was still `new`.
   - The paid email is sent from ONE place in this handler. A second fire-and-forget POST of `{action:'paid'}` used to sit ~140 lines further down under its own copy of the stale guard, so a customer could get two identical letters about one payment; it was removed 2026-09-13 and the awaited call next to the stock deduction is the only one left.
   - On `success` AND `with_designer=true` AND the claim won: fire-and-forget POST `/api/designer-service/on-payment`. The Monobank webhook is not allowed to block on email + Telegram (those would make Monobank retry the webhook on slow APIs), so we don't await.

5. **Designer handoff** (`app/api/designer-service/on-payment/route.ts`):
   - Loads the order + customer (joined customers row, or inline `customer_*` fields for guest checkout).
   - Creates a `design_briefs` row with `status='waiting_brief'`. Token is generated by the `gen_brief_token()` Postgres DEFAULT — server-side capability that the customer can later use to access their brief form without logging in.
   - Sends the brief link email via Brevo (`sendBriefLinkEmail`). Skips silently if no email is on file.
   - Pings the designer Telegram chat with the order summary + brief token.
   - Idempotent: re-running on the same order finds the existing brief and just re-sends the email.

6. **Customer fills the brief.** Hits `/api/designer-service/brief/[token]`, fills the form (occasion, style, photo order, important_photos, title_text, additional_notes), uploads photos to the `design-briefs` storage bucket. `submitBrief()` updates the row to `status='brief_received'`, then `triggerAIProcessing()` fires off the AI photo analysis in the background.

7. **Designer picks up the order** in `app/admin/designer/`, assigns themselves (`orders.designer_id` + `assigned_at`), opens the brief, builds the book in the editor.

8. **Revision round-trip.** Designer hits "Send for review" → creates a `design_revisions` row with its own `client_token`, emails customer the review link. Customer approves or asks for changes (`client_decision` + `client_comments` + `general_feedback`). `revision_count` increments per round; the contract caps at 3.

### Region pricing, currency & ship region

Canonical price is **always UAH**. Two checkout decisions depend on (interface language) × (delivery destination), and both live in one pure module, `lib/payment/pricing-region.ts`, used by the server (authoritative) and the client (display) so "shown == charged":

- **`resolvePriceMultiplier(locale, shipRegion)`** — the international markup (×1.30) applies ONLY at `locale !== 'uk' && shipRegion === 'INTL'`. The markup is a function of locale × shipRegion, **not** of currency. `convertPrice` in `lib/i18n/currency.ts` is now a pure conversion (markup was decoupled from it); storefront cards apply markup via `formatDisplayPrice(...)` using the locale's `defaultShipRegion`.
- **`resolveDisplayCurrency(locale, userChoice)`** — default UAH for uk, EUR otherwise; checkout has a UAH/EUR switcher available to everyone. Display only — charge is always UAH.

**International shipping** is a flat €25 fee (free-shipping disabled — config `free_threshold_eur` = 0; set it > 0 to re-enable a free-over-threshold tier) (`computeIntlShippingUah`, config in `settings('intl_shipping')` = `{free_threshold_eur, flat_fee_eur}`, defaults in `DEFAULT_INTL_SHIPPING`). The threshold/fee are in EUR; the order's marked UAH subtotal is converted via the buffered rate to decide. `/api/orders/submit` computes the fee server-side and stores it in `orders.delivery_cost`; the checkout fetches `/api/exchange-rate` (public: rate + threshold + fee) so its displayed total and free-shipping nudge match the charge exactly. Recipient-pays-on-delivery is **not** available for outbound international (domestic-only), so intl shipping is always prepaid in the order total. NOTE: a uk-locale customer shipping abroad gets no markup (matrix: base UAH) but pays the same flat €25 shipping — fine.

The checkout shipping step now carries an authoritative **UA / INTL selector** (`shipRegionChoice`) that drives the address form (Nova Poshta picker vs free international address), the payment account, the markup, split availability (INTL = full prepayment only, enforced server-side in `/api/orders/submit`), and the currency default. The old late "payment region" modal was removed.

`/api/orders/submit` receives base UAH `subtotal`/`total` + `ship_region` + `locale` + `display_currency`, applies the multiplier itself (a tampered client can't skip it), and **freezes** `ship_region`, `price_multiplier`, `display_currency`, `exchange_rate` on the order.

**EUR rate** lives in `settings('eur_rate')` (`{rate, base_rate, buffer_pct, source, updated_at}`), read server-side via `lib/i18n/exchangeRate.ts` (cached). It's refreshed twice a month (1st & 15th, `0 5 1,15 * *`) by `/api/cron/update-exchange-rate` from the NBU official rate with a margin buffer — predictable price-change dates rather than daily drift.



### Manual order create (parallel entry point)

The Monobank webhook is the path for orders the customer pays online. Most of Diana's real volume comes through Instagram DM, where an admin enters the order by hand in `app/admin/orders/create`. That route (`/api/admin/orders/create`) mirrors the webhook side effects so manually-created orders aren't second-class:

- Inserts an `order_created` row in `order_history` with the source (`manual` / `instagram` / etc.) and `created_by` FK, so the order detail page's history feed shows when and how the order entered the system.
- If `with_designer=true` AND the admin marks the order paid on the form, fires the same `POST /api/designer-service/on-payment` the webhook does — fire-and-forget, no await, downstream is idempotent.

Both entry points converge on the same designer-handoff route, so the brief creation / email / Telegram ping logic lives in one place (`app/api/designer-service/on-payment/route.ts`) regardless of how the order was paid.

The three webhook endpoints, the dual `mono_*` / `monobank_*` order columns, and the historical reference to `design_orders` / `designer_assignments` in earlier drafts of this doc are all artefacts of the same migration episode and have been straightened out — `monobank_*` is canonical, the older alias columns are dead code paths preserved only because dropping them is a DB migration risk for very little gain.

## Partner referral program (travel agencies, bloggers, photographers)

One program, four kinds of partner (`agency_partners.partner_kind`: `travel_agency`, `wedding_agency`, `travel_blogger`, `photographer`). Do not confuse it with the two neighbours: the **friend referral** (`referrals` + bonus balance, `/api/referral/*`) is a customer-to-customer mechanic, and **wedding agencies** at `/wedding-agencies` are a plain B2B discount on `customers.b2b_*` with no commission ledger.

**Flow.** Application (`/travel-agencies/apply` → `partnership_requests`, or a manager's `/api/sales/partner-requests` → `partner_activation_requests`) → manual approval → one `agency_partners` row plus one `promo_codes` row carrying the **same code string** → welcome email with `?ref=CODE` and the cabinet link → visitor lands, `ReferralCapture` stashes the code in `localStorage` → checkout auto-applies it via `/api/promo/validate` → `orders.promo_code` → on the paid transition `processAgencyCommission` writes one `agency_commissions` row → partner cabinet → payout.

**The model is "link only + lifetime binding" (Diana, 2026-09-16).** A client reaches the shop through `?ref=` and the 5% comes off by itself; the code is never shown to them and typing it by hand is refused (`/api/promo/validate` answers "цей код працює лише за посиланням партнера" for any code that belongs to `agency_partners` and did not arrive with `source:'link'`). The welcome email and the partner cabinet show the LINK only — the code survives as an internal identifier visible in the admin. Ordinary promo codes (WELCOME7 and friends) are untouched by any of this.

The **first paid order** with partner attribution binds that buyer's normalised email to the partner forever, in `partner_client_bindings`. From then on EVERY paid order from that email earns the partner 5%/3%, with no link click, no localStorage and no account — the binding is created once and a later click on someone else's link never overwrites it (the email is the primary key, so the rule is enforced by the database rather than by a check that would lose a race between two simultaneous payments). The **discount is not lifetime**: 5% applies only to that first, binding order, and repeat orders are full price with no mention of a partner in the client's UI. Ordinary promo codes work freely on repeat orders and do not block the commission. The 90-day localStorage window governs only the path BEFORE binding; afterwards the email decides and localStorage is irrelevant.

Commission attribution therefore lives in **`orders.referral_partner_id`, not `orders.promo_code`** — the client can type a normal promo over a partner link, or dismiss the partner discount entirely, and the partner still earns. `processAgencyCommission` resolves the partner from that column, then from the binding, then (for pre-existing orders and manual admin entry) from the legacy promo code. Ledger rows carry `kind`: `new_client` for the order that created the binding, `repeat` for everything after, which is what the cabinet splits into separate figures. All the earlier rules still apply to repeat accruals — cancellation reverses only PENDING commissions, self-referral (buyer email == partner email) earns nothing AND creates no binding, `UNIQUE(order_id)` keeps it idempotent, and totals come from `recalc_agency_partner_totals()`.

**One code, two jobs.** The same string is the client's discount (`promo_codes`) and the partner's attribution key (`orders.promo_code`). Both must line up, and since 2026-09-16 they are forced to: `orders/submit` derives `promo_code` from `promo_codes` **by `promo_id`**, never from the request body. Trusting the body meant a request could name a partner's code with no `promo_id` at all — no discount applied, no check triggered, and the partner credited after payment.

**The partner welcome email exists once**, in `lib/agency/welcome-email.ts` (`buildPartnerWelcomeEmail` / `sendPartnerWelcomeEmail`, sent through Brevo, never throws). `POST /api/admin/agency-partners/[id]/resend-welcome` — the admin "Надіслати лист" button — used to carry a full second copy inline, and it had drifted on four counts: it led with the CODE instead of the link, hardcoded the client discount to 5 instead of reading the partner's promo row, knew two of the four partner kinds (a photographer was called "агенцією"), and never mentioned the lifetime binding. A partner re-sent the email therefore read different terms than one who got it at approval. `tests/partner-welcome-email.test.ts` pins all four so the copy cannot come back unnoticed.

**Partner email is normalised inside `createAgencyPartner`** (trimmed, lower-cased, via the same `normalizeBindingEmail` the client binding uses) and an unusable one throws rather than creating a half-dead partner. It used to be each caller's job and only two of the four did it — the admin flow took the address straight from the request body and the photographer cabinet from `photographers.email`. Case never mattered, since every read is an `ilike`; a stray space did, and silently on both sides: `/uk/partner/cabinet` would say "cabinet not found" and the recovery form would answer "sent" while sending nothing. `20260916_normalize_partner_emails.sql` cleaned the existing rows (0 of 3 needed it — insurance, not a cure).

**Partner creation goes through `lib/agency/create-partner.ts` and nowhere else.** The admin approval route, the manager-request approval and the photographer cabinet all call it. It used to be duplicated in `/api/admin/agency-partners` and the copy drifted (no duplicate-email guard, only two of four kinds, wrong wording in the promo note). Code uniqueness is checked in **both** `agency_partners` and `promo_codes` — both carry a unique index, and checking one alone made the other fail with a raw Postgres error.

**Commission rules (Diana, 2026-09-16).** Base is the subtotal **before** the client discount — `total_price` per item, since the discount lives in `orders.subtotal − orders.total` and is never split across items. A **self-referral** (buyer email equals partner email) gets the discount but no commission, and no manager accrual either; the check is inside `processAgencyCommission` because five call sites reach it. Attribution from a stored `?ref=` expires after **90 days** (`REF_ATTRIBUTION_TTL_MS` in `lib/referral/pending-code.ts`); a fresh `?ref=` in the URL is always honoured. On cancellation, `reverseAgencyCommission` flips a **pending** row to `payout_status='cancelled'` — already-paid commissions are left alone on purpose.

**Totals are derived, not accumulated.** `agency_partners.total_earned` / `total_paid_out` are recomputed from the ledger by `recalc_agency_partner_totals(uuid)`, and per-agency aggregates come from `agency_commission_stats()` (both in `supabase/migrations/20260916_agency_commission_integrity.sql`). Read-modify-write on those columns lost updates under concurrent webhooks, and summing the ledger in JavaScript was an unpaginated read straight into gotcha 14.

**Files.** `lib/agency/{create-partner,commission,welcome-email}.ts`, `lib/sales/{commission,attribution,partner-activation}.ts`, `lib/referral/{pending-code,promo-code}.ts`, `components/ReferralCapture.tsx`, `app/[locale]/travel-agencies/*`, `app/[locale]/partner/*`, `app/api/partnership/*`, `app/api/admin/{agency-partners,partner-requests,partnership-requests}/*`.

**RLS.** `agency_partners`, `agency_commissions` and `partner_activation_requests` have RLS on with **zero policies** — deny-all for anon/authenticated, reachable only through the service-role client in API routes. That is deliberate; do not "fix" it by adding a read policy.

**Link clicks (added 2026-09-16).** `referral_visits` records one row per click-through: `referral_code`, `landing_path`, `created_at`, and deliberately **nothing else** — no IP, no User-Agent, no visitor id, no link to `customers`. A row says "this code was opened then, onto that page", which is all a partner needs and is one fewer table holding personal data. It has **no FK to `agency_partners`** on purpose: counting by code over `referral_visits_code_created_idx` is just as fast, and every new foreign key is another place gotcha 12 can fire. Codes are stored upper-case (normalised on both sides) so the match is a plain `=`.

A visit is counted **only when the code arrives as `?ref=` in the URL** — the later pages a visitor browses carry no parameter and are not clicks, otherwise the number would measure browsing depth instead. Repeat opens of the same link inside 24 h count once (`VISIT_DEDUP_WINDOW_MS`), remembered in the visitor's own `localStorage`; the server adds a short in-memory guard keyed on IP+code that is never written anywhere. The rule is `lib/referral/visit.ts` (pure, tested in `tests/referral-visit.test.ts`), the write path is `POST /api/referral/visit` (fired by `ReferralCapture`, always answers 200 so it never becomes an oracle for which codes exist, and only stores a code belonging to an ACTIVE partner). A headless browser with no `localStorage` can still inflate the count, which is why the cabinet shows visits next to paid orders and a conversion figure rather than as a number on its own.

Counting goes through `referral_visit_stats()` from the same migration, never a row fetch: this table fills from shop traffic and grows faster than any of gotcha 14's six, so summing it in JavaScript would hit the silent 1000-row ceiling. RLS on, zero policies, same as the rest of the program.

## Routing & i18n

- All public routes live under `app/[locale]/` — locale is one of `uk`, `en`, `ro`, `pl`, `de`
- Default locale: `uk`
- Middleware handles locale detection and redirects — it is **`proxy.ts` in the repo root, and there is no `middleware.ts`**: Next.js 16 renamed the file, the build log prints it as `ƒ Proxy (Middleware)`, and a search for `middleware.ts` finds only the unrelated `lib/supabase/middleware.ts` helper. It puts the locale prefix on any path that arrives without one (cookie `tm_locale` → `Accept-Language` → `uk`), carries the whole query string across, and sets `tm_locale` — which is why a link like `/unsubscribe?token=…` works and lands on `/uk/unsubscribe?token=…`
- Static labels: `locales/{locale}.json` files, accessed via the `useT()` hook
- DB-driven content (product names, category names, footer sections etc.) uses a `translations` JSONB column with shape `{ uk: {...}, en: {...}, ro: {...}, pl: {...}, de: {...} }`
- The `getLocalized(record, field, locale)` helper in `lib/i18n/localize.ts` reads `translations[locale].field || record.field` (fallback to base column)

Written by Monobank webhook, automation routes, admin order page. `added_by` now carries the acting staff member on the admin PATCH path (`resolveActingStaff()`); it was NULL on all 655 status and payment rows before 2026-09-13, so «who cancelled this order» had never once been answerable. Deliberate trade-off, documented in the function's own header; a failed send assigns too, because the person took the order on either way. Event freshness is decided by the `ts` INSIDE the event, never by arrival time — Brevo does not guarantee order and a deferred can land after a delivered — and the rule lives in `lib/email/delivery-events.ts` (pure, tested in `tests/email-delivery.test.ts`) alongside the event map, the message-id normaliser (both sides are stripped of angle brackets and lowercased, or matching fails silently) and `describeMailRow()` which the order card renders. Campaign mail is NOT covered: `email_campaign_queue` stores no provider message id and the drain writes no `email_logs` row, so delivery statuses today cover per-order mail only. **Duplicate suppression (added 2026-09-13) lives in `/api/email/transactional`, not in its callers.** Four paths confirm one payment — the Monobank webhook, check-payment, «Позначити оплаченим» and admin order creation — and each patched separately would see only itself, which is exactly how two identical «оплату отримано» letters reached a customer. They all funnel through this one route, so the rule sits there: if `email_logs` already holds a row for this `order_id` + `template` with `status='sent'` inside `DUPLICATE_WINDOW_HOURS` (24, a constant in `lib/email/log-outgoing.ts`), the send is skipped and the route answers 200 with `skipped: true, duplicate: true` — an error would only make Monobank retry the webhook forever. It checks the FACT of a successful send, so a failed attempt never blocks a retry, and a failure to read the log lets the mail through (silence about a received payment is worse than a second letter). Guarded actions are `paid` and `shipped`, which describe events that happen once; `placed` is deliberately exempt because the «Надіслати посилання клієнту» button re-sends it on purpose. Pure parts tested in `tests/email-duplicates.test.ts`. **The address a customer is told to write to is `SHOP_CONTACT_EMAIL` in `lib/email/contact-address.ts`, never a literal.** It is NOT the sender address: mail goes out from `hello@touchmemories.com.ua`, whose domain is verified in Brevo so sending works and everything looks fine, while no mailbox exists behind it at all. In the three marketing ones (AbandonedCart, WelcomeSeries, WinBack) that invitation was worded as the unsubscribe instruction, and an earlier draft of this file read that as leaving people with no way out of the mailing list. **That was wrong, and the correction matters because it changes what the defect was.** Marketing mail already carries a working «Відписатися від розсилки» link plus `List-Unsubscribe` / one-click headers, both added by `withUnsubscribeFooter()` in `lib/email/unsubscribe.ts` whenever the caller passes `unsubscribe` — and the abandoned-cart, win-back and welcome-series crons all do. What the dead address really created was a SECOND, competing route out that happened to be broken: a reader who followed the body text instead of the footer wrote to a mailbox that does not exist, got no answer, and stayed subscribed. So the fix was not to re-point that sentence at a live address but to delete it, which was done on 2026-09-13 — the footer is the single way out, and `tests/email-duplicates.test.ts` now fails if the text instruction reappears in any of the three. **Do not add an unsubscribe instruction to an email body: the footer already is one.** `emails/DesignerBriefEmail.tsx` still prints `info@touchmemories.com.ua`, a third address nobody has confirmed is alive. The acting person is resolved by `resolveActingStaff()` in `lib/auth/guards.ts` — `staff` has no auth-user column, it is matched by email — and is passed in the request body to `/api/email/transactional`, which is called server-to-server with the cron secret and so never sees the manager's cookies.

No session meant the field stayed empty forever; nothing anywhere back-linked, and the registration route never touched `orders` at all. By 2026-09-14 that left 64 registered customers with an empty card despite 69 510 ₴ of purchases, plus 2 with a split history. The cause was NOT «bought before registering»: **71 of those 72 orders were placed AFTER registration**, on average 3.2 days later — people who have an account simply check out logged out, and guest checkout is the norm rather than the exception (only ~40% of site orders carry a `customer_id`, steady across July–September). `linkGuestOrdersForCustomer()` in `lib/customers/link-guest-orders.ts` runs over every guest order with the same normalised email, **from `app/[locale]/auth/callback/route.ts` — not from `/api/auth/register`, which nothing called and which is deleted as of 2026-09-14**. That is where it was first put, and it never ran once: both signup forms go straight to `supabase.auth.signUp` and the customer row is created by the `handle_new_auth_user` trigger on `auth.users`, so the route is dead code. It is also broken independently — its `customers` insert names `birthday_day` / `birthday_month` / `birthday_year`, three columns that do not exist, and its failure path deletes the auth user it just created; 35 people entered a birthday at signup and only 5 have one in `customers`, because that route was the only thing that ever wrote it. The linking does NOT live in a DB trigger either: the matching rule is TypeScript with tests over real pairs, and a PL/pgSQL twin would be a second copy of the rule — the same trap the paid-in-full rule fell into. The auth callback is the one server-side point every signup passes through, email confirmation and Google alike, so it does not depend on whoever writes the next login form remembering to call anything. **Matching on email alone is not safe and the data proves it**: one address is shared by a family, and the account «Svitlana Krasnova» is used repeatedly to order for «Ірина Байдакова», while «Julia Savkiv» carried orders for «Савків Наталія» — same surname, different person. It folds ru/uk letter variants and apostrophes, transliterates Cyrillic to Latin, and then requires **two matching name tokens** when both names have two or more — one shared surname is not enough, which is exactly what stops the Savkiv case. A differing phone can only ever force a review, never permit a link. There is deliberately **no list of diminutives**: «саша»/«Олександра» and «Ліза»/«Єлизавета» go to manual review like everything else, because such a list needs endless upkeep and the first missing pair becomes either a wrong link or an inexplicable exception (Diana, 2026-09-14). On the 50 real pairs the rule links 16 and sends 34 to review, with no wrong link among them. Those constraints existed only in prod until 2026-09-14 — the table was created by hand in the Supabase dashboard — which is exactly why every writer got them wrong: the code sent ACTION names (`cookies_accepted`, `terms_accepted`, `account_deleted`), a `source` of its own invention, and a `metadata` column that does not exist. All four inserts were rejected, none of the four routes checked the error, all four answered success, and the table held **0 rows against 366 subscribers**. `supabase/migrations/20260914_consent_log_baseline.sql` now captures the table as it is (it is a no-op against prod) so the rules are readable in the repo, and the action→category translation lives in `lib/consent/log-entries.ts`, pure and tested in `tests/consent-log.test.ts`. Write to it ONLY through `/api/consent/log` (cookie banner, footer subscribe, registration, newsletter popup) or `/api/account/consent-marketing` (the account toggle). **Audit events are not consents and do not belong here**: the data-export and account-deletion inserts moved to `account_audit_log` on 2026-09-14. The `anon_insert_cookie_consent` RLS policy used to demand `consent_type IN ('cookies_accepted','cookies_partial','cookies_rejected')` — values the table's own CHECK forbids, so no anonymous insert could satisfy both rules at once. Harmless while only the service role wrote here, but a trap for the first person to try it from the browser; `supabase/migrations/20260914_consent_log_anon_policy_fix.sql` narrows the policy to the four cookie categories (`essential`, `analytics`, `marketing`, `functional`) and is APPLIED to prod, unlike the baseline snapshot beside it. `terms` and `privacy` are deliberately outside that list: they come from registration, where the person already has a session and `authenticated_insert_own_consent` applies.
- **`account_audit_log`** (added 2026-09-14) — the two events that are NOT consents: `data_export` and `account_deletion`. Deliberately minimal — `event_type`, `created_at`, and a nullable `customer_id` — with no email, no IP and no user agent anywhere in it. `customer_id` is allowed only for an export, where the account still exists and «when did I request my data» is a fair question; for a deletion it is forbidden **by a CHECK constraint, not by convention** (`account_audit_log_no_subject_on_deletion`), because keeping an identifier in the record of someone asking to be erased does the opposite of what they asked. Which deletion request was honoured is evidenced by the account itself: `/api/account/delete` anonymises the `customers` row to `deleted+<id>@touchmemories.deleted`, so the log only has to count events. Written by the service role from those two routes and nowhere else — there is no INSERT policy at all, for anon or authenticated, since the subject of an audit event must not be able to create it. A failed insert is logged and swallowed: neither the right to export nor the right to be deleted may depend on our bookkeeping. Constraints are exercised by `supabase/tests/account_audit_log.test.sql`, which rolls its rows back.
- **Consent for subscribers from before 2026-09-14 lives in `subscribers`, not in `consent_log`, and that is the honest record.** The newsletter popup — the source of 357 of the 366 subscribers — had no consent checkbox and never called the consent route at all until 2026-09-14, and the other entry points wrote nothing because of the defect above. Nothing was back-filled: inventing a consent row dated today for a decision made in June would be a worse record than none. What genuinely exists for those people is `subscribers.subscribed_at` (when), `subscribers.source` (`popup` / `footer` / `unsubscribe` — through which form) and `subscribers.unsubscribe_token` (every one of the 366 has one, so the way out has always worked). Treat that trio as the evidence of consent for anyone subscribed before 2026-09-14; `consent_log` is authoritative only from that date forward.
- **`expenses`** + **`expense_categories`** — finance module. `expenses.extras` JSONB captures form fields beyond the explicit columns.
- **`salary_calculations`** + **`salary_periods`** + **`staff_shifts`** + **`staff_work_log`** — payroll. `is_locked` on salary_calculations freezes paid periods from re-computation. The earlier `salary_records` name in this doc referred to a table that never existed — the canonical name is `salary_calculations`.
- **`qc_error_log`** — production QC errors attributed to staff for salary deductions
- **`stock_alerts`** — out-of-stock / low-stock notification log so we don't double-notify
- **`social_conversations`** + **`social_messages`** — AI chatbot social inbox (Instagram / FB / Telegram Business). `lib/chatbot/core.ts` handles auto-replies; admin/social-inbox is the manual-reply UI. A trigger on `social_messages` insert updates the conversation's `last_message_at` + `is_read=false` (when sender is customer). **Nothing here is ever deleted** — there is no retention job in the codebase, no pg_cron job in the database (the extension is installed, `cron.job` is empty), and the account-deletion route does not touch these tables, so a customer who deletes their account keeps their correspondence. As of 2026-09-14: 838 conversations, ~66 000 messages since 2026-08-11, all Telegram, 17 MB.
- **Conversation → order link is computed, not entered** (2026-09-14, `supabase/migrations/20260914_social_conversation_order_link.sql`). `social_conversations.order_id` / `customer_id` had existed from the start and were empty in all 838 rows: the only writer is `processReceivedMessage`, which needs the client to quote an order number AND the business mode to be `auto`, and the mode has been `off` since day one. `public.link_social_conversations(p_apply, p_name_phase)` fills them in one pass: order number next to a marker word → `link_confidence='order'`, phone (last 9 digits, separators between digits stripped first) → `'phone'`, rare name token → `'name'`. It only writes when `p_apply=true` and it never deletes. First run: 29 by number, 513 by phone, 296 unlinked. **`link_confidence IS NULL` means «no link found», NOT «no client here»** — all 296 unlinked conversations are dialogs Diana herself replied in; they simply never carried a phone or an order number. The name phase is OFF by default because in this direction it is unreliable: a photographer's dialog dictating her clients' details matched 20 different orders. A retention rule must not be written against these columns until that is understood.
- **`certificates`** — gift certificates. Canonical name; an earlier alias `gift_certificates` was unified into this table. Schema covers money + product certificates, electronic + printed, plus the 7-day-before-expiry reminder flag the cron route uses.
- **`gift_hints`** — anonymous "gift hint" submissions (public insert, admin read)
- **`order_tags`** + **`order_tag_assignments`** — many-to-many order-tag linkage (separate from the `tags` text[] column on orders, used by the admin UI for colour-coded tags)
- **`photobook_projects`** — legacy table, last writes March 2026. New saves go to `projects`
- **`projects`** — saved editor sessions (photobook, travelbook, magazine, wishbook). Columns: `pages_data`, `cover_data`, `overlays_data`, `uploaded_photos`. The `overlays_data` jsonb bundle holds `pageStickers`, `pageShapes`, `pageBgs`, `freeSlots`, `qrOverlays`, `generatedQRCount` — everything the editor renders on top of `pages_data` that wouldn't otherwise be persisted
- **`footer_sections`** — site footer content (has `translations` JSONB, application is incomplete — see Known gaps)

Storage buckets (`storage.buckets`, not tables): `category-images`, `db_backups`, `design-briefs`, `order-files`, `photobook-uploads`, `poster-exports`, `products`, `touch-memories-assets`, `travel-covers`, `videos`. `db_backups` previously appeared in this doc as a "missing table" — it's a storage bucket and exists.

Antigravity often pushes to the same repo concurrently. Always start with:
```bash
git fetch origin && git reset --hard origin/main
```
After making changes, before pushing, rebase and check for conflicts. If Antigravity already applied something similar, cherry-pick only the new commits.

### Patch protocol
Use `str_replace` for code patches, **not** `git apply`. The `git apply` workflow has caused issues in past sessions.

### TypeScript check
```bash
npx tsc --noEmit | grep error TS | grep -v TS2307
```
The `-v TS2307` filter intentionally hides module-not-found errors that are not relevant to current changes.

11. **Security hardening** — full audit on 2026-04-29 found 24 critical/high/medium issues across RLS, API auth, webhook verification, and dependency vulnerabilities. Three migrations + extensive code changes resolve them. **All applied to prod 2026-04-29.**
    - `20260429_security_hardening.sql` — enable RLS on `magazine_briefs` (was off; PII questionnaires were anon-readable), drop public SELECT on `subscribers` / `wishlists` / `gift_certificates` / `inventory_movements`, drop `Free Designer Orders Read` (anon-leaked customer PII for designer-service orders), drop anon FOR ALL on `photobook_projects` / `recipes`, restrict `bank_accounts` / `fiscal_accounts` / `np_accounts` to admin only, drop `staff` "any authenticated reads" policy, drop `design_briefs` / `design_revisions` `USING (true)` policies, lock down orphan tables from sibling projects.
    - `20260429_security_hardening_admin_check_fix.sql` — fixes the previous migration's admin check. The first attempt used `EXISTS (admin_users WHERE id = auth.uid())` but `admin_users.id` is its own UUID, NOT `auth.users.id`. Replaced with the existing `is_admin()` DB function (matches via `auth.jwt()->>'email'`).
    - `20260429_close_customer_projects.sql` — `customer_projects` had a policy literally named "Admin full access" but with `USING (true)` and no role restriction; full table was anon-readable. Closed with admin/owner policies; the customer review link path now goes through `/api/review/[token]/[action]` with token-validated service-role access.

    Code-side fixes:
    - `lib/auth/guards.ts` — new `requireAuth` / `requireAdmin` / `requireOwnerOrAdmin` helpers for API routes.
    - 24 `/api/admin/*` routes — added `requireAdmin()` at the top of every handler. Previously they used the service-role client with no auth check; anyone could GET/PATCH any order, change `payment_status`, etc.
    - 5 dangerous non-admin routes guarded similarly: `/api/orders/[id]/{duplicate,send-email,create-ttn}`, `/api/production/queue`, `/api/monobank/sync-balance`.
    - `/api/orders` (no params) was leaking ALL orders with customer PII to anyone — now requires admin.
    - `/api/orders/track` — added input validation to prevent PostgREST `or()` filter injection via the `contact` field.
    - `/api/monobank/webhook` — was silently skipping signature verification when the `X-Sign` header was missing (trivially forgeable: anyone could mark an order as paid). Header now required when `MONOBANK_PUB_KEY` is set; 503 in production if the env var is missing.
    - `app/[locale]/review/[token]/{page,ReviewPageClient}.tsx` — switched to use `/api/review/[token]/[action]` server route + admin client for the page query, so token-based public review still works after RLS lockdown.
    - `npm audit fix` ran: 3 vulnerabilities remain unfixed and are accepted risks: `xlsx` (no upstream fix; we generate xlsx, never parse untrusted input), `request` + `form-data` (transitive via `node-telegram-bot-api` → no maintained alternative; runs server-side over HTTPS to Telegram API).

13. **Twenty-six `app/api` routes have no caller anywhere, and the list is in `docs/dead-routes.md`** (2026-09-14). Read that file BEFORE adding logic to a route you did not personally trace a call into. This gap exists because of a concrete miss on 2026-09-14: guest-order linking was written into `/api/auth/register`, which looked alive, was named exactly right and contained sensible code — and had zero callers, so it never ran once, and that only surfaced when someone counted how many orders it had linked. The answer was zero. `scripts/dead-routes.mjs` re-measures the list; its output is raw and needs reading by a human, because a mention in this doc or in a migration comment counts there as a mention while being no call at all (that is how `/api/admin/salary/qc` stays out of the script's list but belongs on the human one). Of the twenty-six, six are alive and simply called from outside the repo (Make.com, ManyChat, the Google and Meta feed crawlers, `curl` by hand), two are the deliberately manual one-off backfills, four are public-looking enough that Diana is checking them herself, and fourteen have no known caller at all — fifteen once `/api/admin/salary/qc` is added back from the script's blind spot. Nothing on the list has been deleted except `/api/auth/register`; deletion is Diana's call.

12. **Dashboard and analytics still report `total`, not money received** (open, 2026-09-14 — deliberately NOT part of the four-consumer fix in `1513a701`). `/api/admin/dashboard` computes `todayRevenue` as the sum of `total` over every order created today regardless of payment, and `awaitingPaymentSum` as the sum of `total` where `payment_status = 'pending'` — the full order value, not the outstanding balance. `/api/admin/analytics` reads `total` for revenue, the period-over-period change, the 30-day chart and the COGS match. So both pages answer «how much was ordered», while the payments page, client `total_spent`, the expenses P&L and photographer totals now answer «how much came in», and the two sets of numbers disagree on every partially-paid order. Moving them over means `receivedAmount()` in the routes AND the `get_daily_revenue` SQL function, which is a second copy of the rule living in the database — change one without the other and the 30-day chart silently keeps the old answer.
