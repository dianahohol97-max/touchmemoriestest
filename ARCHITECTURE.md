## High-level stack

- **Framework:** Next.js 16 (Turbopack) App Router · TypeScript
- **Styling:** Tailwind + shadcn/ui (Radix primitives)
- **Database:** Supabase (Postgres + Auth + Storage). **PostgREST caps every request at 1000 rows and does it SILENTLY** — no error, the response is simply short — so any `.select()` that can match more than a thousand rows needs a `.range()` loop (`const PAGE = 1000; for (let from = 0; ; from += PAGE) { … .range(from, from + PAGE - 1); if (!data || data.length < PAGE) break; }`, the shape used in `/api/admin/clients`). This is the quietest class of bug in the codebase: it looks like nothing until the table crosses the line, and then reports just start under-reporting. On 2026-09-14 five places were already over it — both client lists, `/api/orders`, the new-vs-returning split in admin analytics, and the design-lifecycle cron — and the payments page had been truncating for some time before that. A paginated loop also needs an explicit `.order()`: without one PostgREST's row order is unspecified and pages can overlap or skip. Queries bounded by a filter (`.eq('order_id', …)`) or asking only for a count (`head: true`) are not affected. Where a query is near the line but still under it, the comment above it carries the measured row count and the date it was measured, so the next reader sees a number rather than an assumption.
- **Hosting:** Vercel (team `team_Qve9hriFT9sNYnjWZolAcFXl`, project `prj_Oz13dkGF3W1JvSVToT8WvZBseBba`)
- **Payments:** Monobank (UA + international dual-account routing via `bank_accounts.region`; charge always in UAH, EUR shown via buffered NBU rate)
- **Email:** Brevo
- **AI:** Anthropic SDK (chatbot, generation tasks)
- **Drag/drop:** dnd-kit
- **Canvas / image editing:** Fabric.js, html2canvas, jspdf
- **Background removal:** @imgly/background-removal

## Editor architecture (the big one)

The photobook/travel book editor is the most complex part of the codebase. **80% of "I can't find why this is broken" debugging happens here.** Read this section before touching it.

### Core files
- **`components/BookLayoutEditor.tsx`** — the main editor (6175 lines). State, layout, photo placement, text, frames, stickers, navigation, save/preview/order. This file is the editor.
- **`components/CoverEditor.tsx`** — separate cover editor, called by BookLayoutEditor for the cover spread.
- **`components/FramesLayer.tsx`** — overlay layer for PNG + SVG frames on a page.
- **`components/FreeSlotLayer.tsx`** — non-template free-floating photo slots with their own DPI checks.
- **`components/BookPreviewModal.tsx`** — preview of the finished book. Renders backgrounds, photo slots, frames (PNG+SVG), shapes, stickers, QR overlays, and the kalka page. Multi-slot layout rendering is still pending — it currently uses single-slot getSlotDefs only.

### Supporting files in `lib/editor/`
- **`types.ts`** — `PhotoData`, `BookConfig`, `CoverState`, `CoverDecoType`, `LayoutType`, `SlotData`, `TextBlock`, `Page`. **This is now genuinely the source of truth** and the editor imports from it. Until 2026-08-31 it only claimed to be: nothing imported it, and every one of these shapes was ALSO declared privately inside `BookLayoutEditor.tsx` (and two of them a third time in `BookPreviewModal.tsx`). The copies here had drifted far behind — `PhotoData` 5 fields against the real 13, `SlotData` 5 against 11, `LayoutType` a bare `string` against a ~200-member union — so anyone who followed this doc was coding against shapes that had not been accurate for a long time. Change a shape here; do not re-declare it in a component.
- **`constants.ts`** — 98 fonts (`FONT_GROUPS`, `FONT_DATA` with `cyr` flag — a flag that lied for four families until 23.09.2026 and is now pinned against the files by `tests/editor-fonts-pack.test.ts`), `GOOGLE_FONTS_URL`, `EDITOR_FONTS_CSS_URL`, `FONTS_NOT_ON_GOOGLE`, decoration variants (acryl, photovstavka, flex, metal, gravira), leatherette/fabric/velour colours
- **`page-templates.ts`** — 64 spread layouts (`PAGE_TEMPLATES`)
- **`cover-templates.ts`** — 30+ cover presets, filterable by `tags` (`photobook` / `magazine` / `journal` / `travelbook` / `wishbook`)
- **`slot-defs.ts`** — slot geometry definitions for each layout
- **`auto-build.ts`** — automatic spread building from a photo set
- **`pricing.ts`** — dynamic price calculation: base + cover + size + pages + decorations + kalka + endpaper

### Editor sub-components in `components/editor/`
- **`FontPicker.tsx`** — visual font picker with previews. **Note:** the `kalka` (acid paper) flow still uses a basic `<select>` with 10 fonts — replacing it is a known TODO.
- **`CoverTemplatesPicker.tsx`** — filtered by `productType`
- **`PageTemplatesPicker.tsx`** — spread layout picker
- **`AutoBuildModal.tsx`** — guides the user through auto-build
- **`PhotoPanel.tsx`, `PhotoEditingPanel.tsx`** — photo upload, crop, zoom inside slot
- **`TextPropertiesPanel.tsx`** — text styling
- **`TemplatePanel.tsx`, `EditorSidebar.tsx`, `EditorToolbar.tsx`, `EditorTopBar.tsx`** — UI shells
- **`SpreadNavigation.tsx`** — page-by-page navigation
- **`PreviewModal.tsx`** — local-scope preview (different from the BookPreviewModal at component root)

### Cover text model (front + back)

The cover has two surfaces — front and back — and both can carry free-positioned text:

- **`coverState.printedTextBlocks`** — front-cover text on printed covers (magazine / journal / photobook printed / travelbook / wishbook / scrapbook / graduation). Rendered by `CoverEditor`.
- **`coverState.extraTexts`** — front-cover text on soft covers (велюр / тканина / шкірзамінник albums). One-shot inscription priced at +180 ₴ via `inscriptionMethod` (`flex` or `graviruvannya`). Rendered by `CoverEditor`.
- **`coverState.backCoverTexts`** — back-cover text on printed covers. Same shape as `printedTextBlocks` (`{id,text,x,y,fontSize,fontFamily,color,bold}`, percent-positioned). Rendered by `CoverView` directly (the back cover lives in `CoverView`, not in `CoverEditor`). Free, no surcharge. Not supported on soft covers — the front-cover `extraTexts` flow already covers that audience.

All three lists are serialised in `coverState` and persisted automatically via `cover_data` on `projects` (so saved sessions, the cart payload, and the "Замовити повторно" replay flow get them for free). The cart `options` map surfaces back-cover text as `'Текст на задній обкладинці'` when present so production sees the exact strings the customer placed.

The editor's "Текст" tab on `currentIdx === 0` shows two buttons for printed covers: one for the front and one for the back. Both desktop and mobile have the pair.

### Product types the editor handles
The editor switches behaviour based on slug:
- `photobook` (photo book — default)
- `travelbook` (travel book)
- `magazine` / `journal` / `zhurnal` (glossy magazine — different cover templates, different fonts)
- `wishbook` (wishbook — cover-only, simplified UI, hides spread navigation)

The product-type detection is in BookLayoutEditor via `_slug.includes('...')` checks.

### Known editor pain points (debug-time savers)
- **Antigravity sometimes pushes broken `useT()` placement.** Run `npx tsc --noEmit | grep error TS | grep -v TS2307` after pulling. The `TS2307` filter is intentional — it ignores module-not-found errors that are not relevant.
- **i18n in DB-driven content** (Footer, products, categories) requires the `getLocalized()` helper. Footer still uses raw fields in some places — this is a known incomplete task.
- **Frames are currently overlays only.** They render on top of photos but the photo isn't constrained to the transparent area of the frame. Making frames into actual photo slots (PNG-on-top, photo underneath in transparent zone, with crop/zoom inside the frame) is the biggest open editor task.
- **`BookPreviewModal` does not yet support:** multi-slot layouts (uses single-slot getSlotDefs), crop/zoom inside slots (photos render with objectFit:cover only). Frames, shapes, stickers, QR overlays, and cover stickers ARE rendered.
- **`SpreadNavigation` keyboard arrow keys** sometimes conflict with text-editing inside slots — this is by design (focus check), but it can confuse first-time editors.

### Overlay z-order (unified layer stack)

All four overlay types — text blocks, shapes, stickers, QR codes — share a single z-order namespace per page via an optional `zOrder?: number` field on each object. This lets the user freely interleave them: text under a coloured rectangle, sticker above a frame, etc. Rendering uses `zIndexFor(obj.zOrder)` from `lib/editor/zOrder.ts`, which returns `Z_OVERLAY_BASE (100) + (zOrder ?? 0)` — putting the whole overlay stack above photo slots (zIndex 2) and below editor chrome (zIndex 50+).

When the user selects an overlay (click/tap), a small floating `ZOrderToolbar` (`components/editor/ZOrderToolbar.tsx`) appears with four buttons: send to back / send backward / bring forward / bring to front. The toolbar is rendered as a sibling inside the overlay's wrapper, so it sticks above the selected element. Handlers funnel through `zOrderAction(kind, id, pageIdx, action)` in `BookLayoutEditor`, which dispatches to the right slice of state (pages.textBlocks, pageShapes, pageStickers, qrOverlays). All four mutations push history before applying so undo works.

When a new overlay is created (`addShape`, new text, new sticker, new QR), it gets `zOrder: nextOverlayZ(pageIdx)`, which is `max(zOrder) + 1` across ALL overlay types on that page — so newly-placed objects always land on top of the current stack.

`zOrder` is intentionally optional (`?: number`) so saved projects from before this feature continue to render. Undefined is treated as 0 everywhere — old objects appear at the bottom of the new layer system and the user can re-stack them via the toolbar.

Cover overlays (pageIdx === 0) don't have the z-order toolbar yet — covers are simpler decoration surfaces and there hasn't been demand. The infrastructure is type-compatible (Shape/sticker types include zOrder), so adding it is a small follow-up if needed.

## Print render pipeline (added 2026-08-06)

Production files are made by the **Railway render service** (`render-service/`, headless Chromium + sharp), which screenshots the app's `/print/[projectId]` page (a clean, chrome-free render via `BookPreviewModal` in print mode — no trim guides, page digits, «ЗАДНЯ» labels or fake spine bands) at 300 DPI. Key facts:

- **Output shape:** travel books & magazines export page-by-page, named `01.jpg…NN.jpg` per the print partner's checker; soft-cover magazines also split the cover into `00_cover_back/front.jpg`; hard covers stay one wrap sheet (`00_cover.jpg`); photobooks export 2-page spreads (`NN_spread.jpg`). Empty forzats (forzats-as-extra-pages model, no content) are skipped and pages renumbered.
- **Travel book page geometry:** sold as «20×30» but printed on **210×297 mm** pages (partner's hard requirement) — size key `travelbook` everywhere (editor proportions, `lib/print/geometry.ts`, render service). It is NOT the photobook `20x30` (200×300).
- **A spread is TWO WHOLE PAGES, never one double-width sheet.** `mmToPx` rounds, and the two forms disagree: `mmToPx(2 × 210) = 4961` (odd, cannot halve) versus `2 × mmToPx(210) = 4960`. The service derives the spread from `pagePxW = mmToPx(page.w)`, so both halves come out at exactly one page. Measuring the spread on its own gave halves of 2480 and 2481 px, and 2481 px is 210.06 mm — the partner's checker measures to one decimal and rejected every second page («ширина 210.1 і не є рівна 210»), failing whole travel book and hard-journal uploads. 30×30 had the same latent defect (300.0 / 300.1). The `?w=` the service passes to `/print` is that same per-page width, so the capture is never resampled either.
- **Storage layout:** `guest/pb-…/print/` for order-time uploads, `drafts/<uid>/<projectId>/print/` for draft-based projects. The folder is ALWAYS unique per project — a shared `drafts/<uid>/print` folder once let one order's re-render overwrite another's cover.
- **Registration is triple-redundant:** (1) `render-order` awaits the render and registers `order_files` rows — dies on big books (maxDuration); (2) the service POSTs a completion callback to `/api/print/render-complete` with the uploaded paths; (3) the hourly `reconcile-print-files` cron lists each recent order project's print folder and registers anything missing. All three go through `lib/print/register-export-files.ts` and are idempotent.
- **Stale-deploy detection:** the service's `/health` and its completion callback report `RAILWAY_GIT_COMMIT_SHA` — check it against origin/main before debugging «фікс не працює».
- **Railway rebuilds ONLY on `render-service/**` changes** (`render-service/railway.json`, `build.watchPatterns`, added 2026-09-22). Until then the service redeployed on EVERY push to main, and a redeploy kills the container mid-render: the browser dies with «Target page, context or browser has been closed» and the next call gets Railway's own 502 «Application failed to respond». Two days of the error log say it plainly — twelve `[render-order] partial render` plus six `[render-complete] неповний макет`, and the 502 that left TM-001352's переекспорт (project `e3d7c492`) with zero files landed at 15:46:19 on 22.09, two minutes after commit `e5d15206` was pushed. That commit was an RLS fix; the three before it were blog OG-image work. None of them touched the render service, and all of them restarted it. If a render-service change ever stops deploying, the watch pattern is the first suspect: Railway silently skips a push that matches nothing, so confirm with `/health` (its `commit` must equal origin/main) rather than assuming the build ran.
- **An aborted run is retried, a bad layout is not** (2026-09-22). `render-order` asks the service again when a run was CUT SHORT from outside, and only then. The two signatures are «Target page, context or browser has been closed» (Chromium died mid-run) and Railway's own 502 «Application failed to respond» (no container to answer); everything else — «aspect mismatch», «no spread element», a storage refusal — is a property of the layout and a second attempt returns it unchanged. The rule is `lib/print/render-retry.ts`, pure and pinned by `tests/render-retry.test.ts`, because this line is what decides between wasting two minutes of function time and printing a book with a hole in it. At most 3 attempts, 15 s then 45 s apart, and a new attempt never starts without time left inside `maxDuration` to register the files. The retry asks for the SHEETS THAT FELL, not the whole book: `POST /render` takes `only: [2, 7]` (the same numbers it reports in `failed[].spread` / `failed[].page`) plus `subset: true`. That flag matters as much as the retry — it travels into the completion callback, and `/api/print/render-complete` refuses to prune on a subset run. Without it a докат of two sheets reads as a successful render that produced two files, and the prune deletes the other eighteen: TM-001342's defect again, from the other end. If every attempt fails the layout stays marked incomplete (`ok: false`, no prune, «РЕНДЕР НЕ ВДАВСЯ» on the order) — silence is the one outcome that is not allowed.
- **An empty forzat is skipped, a PAID empty forzat is reported** (2026-09-22). The service does not upload a blank endpaper — the workshop asked not to receive blank sheets — and that rule is right until someone has paid for the print. Then the same skip is a silent loss: no `f1.jpg` in the folder, one line in Railway's console, nobody told. `lib/print/forzat-expectation.ts` holds the whole rule, pure and pinned by `tests/forzat-expectation.test.ts`: whether the option was paid (the predicate is word-for-word the one that charges the money in `lib/products.ts` — let them drift and the check either goes quiet on a paid forzat or shouts at a free one), which sides, and which files are missing. It feeds the admin's «Перевірити макет» and the `no_forzat` signal of the lost-order watchdog. Nothing about what goes to print changed. **The payment itself lives in `config.endpaperPaid`**, written by the editor beside the config; `enableEndpaper` is a different thing — the configurator's answer to its own question, and for a soft-cover magazine it can only ever be false, because `shouldShowEndpaperOption()` shows that checkbox for travelbooks and hard covers only. A design saved before `endpaperPaid` existed recovers the payment from its own `cart_payload.options` at open time (`resolveEndpaperPaid`, read-only, nothing written back); saved beats cart, and the weaker source never cancels the stronger one. Where `cart_payload` is the bare `{ id }` marker and both those sources stay silent — six of the twenty designs on paid-forzat orders on 2026-09-23 — `openDesignInConstructor` asks `GET /api/projects/[id]/endpaper-paid`, which reads `orders.items` with the admin client because RLS keeps `orders` away from the browser. That route matches the line BY KEY (gotcha 18) and allows exactly one keyless pairing, a single-item order whose only project this is; anything else answers `null` rather than guessing, because a design unlocked by somebody else's payment looks sound right up to the invoice. It writes nothing. Two orders, TM-001309 and TM-001091, had `endpaperPaid` put into their config by hand before the route existed.
- **Журнал з м'якою обкладинкою віддається одним PDF, і порядок у ньому фізичний** (2026-09-23). Специфікація друкарні: передня обкладинка → форзац 1 → сторінки 01…NN → форзац 2 → задня обкладинка, один файл на весь журнал. Досі порядок рахував `sortPagesForPdf`, а він знає рівно два правила — обкладинка перша, далі за номером, — і обидві половини обкладинки приходять із `page_number = 1`, бо `exportRowsFromPaths` читає префікс `00_` однаково для `00_cover_back.jpg` і `00_cover_front.jpg`. Нічия розв'язувалася назвою, а за абеткою `back` раніше за `front`, тож у друк ішов PDF, де аркуш 1 — ЗАДНЯ обкладинка, аркуш 2 — передня, далі одразу зміст, а задньої в кінці немає взагалі (TM-001352, помічено очима на відео). Рішення тепер у `buildPdfSheets` (`lib/export/layout-pdf.ts`, чисте, пінується `tests/layout-pdf.test.ts`), і набір впізнається ЗА ФАЙЛАМИ, а не за slug: імена `00_cover_front.jpg` / `00_cover_back.jpg` робить рівно один шлях — `splitCoverPages` у render-service, тобто м'яка обкладинка. Тверда лишається одним аркушем-розворотом (`cover.jpg`), фотокнига — розворотами, і для них порядок той самий, що був. **Білий аркуш на місці форзаца, якого немає** (Діана, 23.09.2026): місце мусить бути зайняте, інакше сторінки зсуваються на одну і права стає лівою. Умова навмисно «файлу немає», а не «не оплачено» — оплату в цьому місці не видно, а плутати ці дві речі не можна: TM-001352 оплатило обидва форзаци, а f1 порожній і файлу не має; TM-001299 не оплатило жодного, а обидва намальовані й файли є, і білий аркуш за ознакою оплати затер би там чужу роботу. Розмір білого аркуша береться в ПЕРШОЇ сторінки журналу, яку адмінка міряє наперед саме тому, що форзац 1 стоїть перед нею. Набір у теці не змінюється нічим: рендер-сервіс так само не вантажить порожній форзац, сторож тихих втрат (`no_forzat`, `short_print`) рахує ті самі файли, і жодне замовлення не потребує перегенерації.
- **Шрифти друку лежать у нас, і аркуш не знімається, поки вони не завантажились** (2026-09-23). `/print` підключав `GOOGLE_FONTS_URL` звичайним тегом, і всі 98 родин качав сам Chromium на Railway. Невдалий запит там не видно нічим: перевіркою було `await document.fonts.ready`, а вона означає «завантаження, яке йшло, скінчилося», і резолвиться однаково — і коли файл приїхав, і коли впав. Виміряно в тому самому Chromium: із заблокованою таблицею стилів `document.fonts` порожній, а `document.fonts.check()` для будь-якої родини відповідає `true`, тож очевидна наступна перевірка теж сліпа; у другому досліді впала САМЕ кирилична підмножина при живій латинській, і аркуш вийшов наполовину авторським, наполовину системним. Тепер `public/editor-fonts/` несе ті самі woff2, які віддає css2 (416 файлів, усі підмножини всіх 97 родин, 6,4 МБ), з тими самими дескрипторами — `font-weight: 400`, ті самі `unicode-range`, переписаний лише `src`, — тож вигляд не змінився: піксельне порівняння того самого рядка в Chromium дає однаковий хеш у кожній родині, яку Google встиг завантажити. Збирає пакет `scripts/build-editor-fonts.py`, а `tests/editor-fonts-pack.test.ts` не дає додати шрифт у `FONT_DATA` без файлів — це і є механізм для нових шрифтів — і тримає перелік із восьми місць, які ще ходять у Google, щоб він лише коротшав. З 23.09.2026 той самий файл підключають і всі конструктори, тож екран і друк читають один байт, а `GOOGLE_FONTS_URL` прибрана зовсім. Сторож перед знімком (`lib/print/font-audit.ts`, дзеркало в `render-service/server.ts`, як у `pageHasContent`) звіряє КОЖЕН символ аркуша: чи є грань цієї родини, яка його покриває, і чи вона `loaded`. Зупиняють аркуш лише ті два випадки, які лікуються повтором — наш CSS не доїхав і файл підмножини не доїхав, — і вони йдуть у наявний докат (`only`, `subset`), бо «шрифт не завантажився» додано в `TRANSIENT_PATTERNS`. Родина поза набором (Georgia зі старої панелі, два макети) і відсутні гліфи (кирилиця в Lato, дванадцять макетів) рендер НЕ зупиняють — повтор їх не лікує ніколи, а відмова зробила б ці макети недрукованими назавжди, — але їдуть полем `fontNotes` у колбек і осідають у рядку «останній рендер». `Kyiv Type Sans` Google не віддає взагалі (окремий запит: «400: Font family not found», у спільному запиті назва мовчки випадає) і прибрана з `FONT_DATA`, бо в жодному макеті її не було; `FONTS_NOT_ON_GOOGLE` лишилася порожнім механізмом на наступний такий випадок.
- **Постери НЕ проходять через `/print`, і це свідомо** (2026-09-24). `RAILWAY_RENDERABLE` у `app/api/print/render-order/route.ts` — allowlist: надіслати самоскладений виріб на Railway означало б зняти порожню книжкову сторінку, а режим заміни поклав би цей білий аркуш поверх справжнього файлу. Друкарський файл постера збирає БРАУЗЕР КЛІЄНТА в момент «Додати в кошик»: зоряна карта малює canvas у 300 DPI (`PRINT_SCALE = 4.2` у `StarMapPreview`, A4 ≈ 2500 px) і віддає його в bucket `poster-exports`, постер робить те саме через `lib/poster-render.ts`, перемальовуючи з оригіналів у фізичному розмірі. Файл реєструється рядком `order_files` (`file_type = 'export'`), а невдача ставить мітку `export_failed_<id>`, яку оформлення перетворює на попередження в замовленні. Друга точка входу — кнопка «Зібрати постер з дизайну» в адмінці: той самий рендер, але в браузері менеджерки. Шрифти тепер чекаються по-справжньому: `loadPosterFonts()` питає `document.fonts.load(spec, text)` по САМИХ СИМВОЛАХ кожного напису і розрізняє ті самі два випадки, що й сторож аркуша — родина поза пакетом (`not-in-pack`) тільки звітує, бо повтор її не лікує, а ненавантажений наш файл (`not-loaded`) зупиняє збирання в адмінському шляху, де людина поруч і може повторити. У клієнтському шляху відмови немає навмисно: растр знімається на тій самій машині, що показувала прев'ю, тож людина отримає надрукованим те, що бачила. Раніше тут стояла `await document.fonts.ready`, і єдиний друкарський файл TM-001090 вийшов із неї системною зарубкою. **Наслідок для перевірок:** постер міряється не книжковою міркою — `verifyOrderPrint` упізнає його ЗА ФОРМОЮ (`pages_data[0]` як конфігурація, нуль сторінок) і мовчить про сторінки, обкладинку й слоти, а шрифт читає окремий обхід `collectPosterFallbacks`, бо книжковий нульову сторінку пропускає. Ознака `no_layout` сторожа тихих втрат постерів не стосується (`BOOK_SLUG_RE`), а аудит `auditPrintArtifacts` — стосується (`RX.self`) і вимагає рядок `export`. `«Переглянути макет»` для постера не працює: `/print` гілки для нього не має.
- **Photo readiness:** before each screenshot the service waits for every `<img>` to load AND `decode()` (bounded 45s/photo) — a streaming JPEG at screenshot time produced distorted photos with blank bands.
- **Trim guides for human review:** the admin order page's «Переглянути макет» opens `/print?guides=1`, which overlays per-product cut lines on every content spread — cut frame at the visible edge, a gutter cut line only for page-split products (travel/journals), and a per-product safety zone (`photobook_sizes` margins, min 3 mm) — plus a Ukrainian legend. Guide math lives in `lib/print/trim-guides.ts` (pure, tested in `tests/trim-guides.test.ts`) on top of `deriveGeometry`. Guides are IGNORED whenever `?w` is present, so the render service's screenshots can never carry them. The cover gets its own guides too: in guides mode /print renders it in the PRINT SHEET's proportion (same printPageW/printPageH/printCoverMm path the render service uses, just at screen width) and overlays the cut frame plus an orange fold line — `COVER_FOLD_MM` in trim-guides.ts mirrors the editor's `COVER_BLEED_MARGINS` (partner spec, May 2026); change one → change both, the tests pin the admin side.

## Telegram Business monitoring (added 2026-08-10)

Diana's personal Telegram dialogs with clients are monitored by the public bot (Софія) through **Telegram Business** (requires Telegram Premium on her account; connected in Settings → Telegram Business → Chatbots). No group chats, no bot visible to clients.

- **Webhook:** the existing `/api/chatbot/telegram` route also handles `business_connection` (stores connection state in `settings('telegram_business_connection')`) and `business_message`. Diana's outgoing replies are recorded as `human_manager`, client messages as `customer` — everything lands in the same `social_conversations` / `social_messages` tables as Instagram, so `admin/social-inbox` shows all channels.
- **Modes** (`settings('telegram_business_mode')`): `draft` (default — AI reply is sent to Diana as a suggestion in her chat with the bot, never to the client), `auto` (bot answers the client on behalf of her account via `business_connection_id`; requires the "reply" permission, degrades to draft without it), `off` (record only). Flipping the mode is a settings row update, no deploy.
- **Human-is-in-charge rule:** after Diana replies manually in a dialog, the bot stays silent there for `settings('telegram_business_human_silence_hours')` (default 3).
- **Watchdog cron:** `/api/cron/social-unanswered` (every 30 min, 08:00–22:30 Kyiv) alerts in Telegram about dialogs where the last message is from a customer older than `settings('social_unanswered_hours')` (default 3h) and about `needs_human` escalations. Muted on purpose: dialogs with status `human_handling`, and dialogs a manager replied to within `settings('social_watchdog_active_hours')` (default 24h — the "it's in someone's folder" equivalent, since bots can't see Telegram folders). A dialog re-alerts only every `settings('social_watchdog_realert_hours')` (default 3h; state in `settings('social_watchdog_alerted')`). `?preview=1` returns the payload without sending. **The alert names the dialog and how long it has waited, and never quotes the message** (2026-09-14): `text` was removed from the `WaitingDialog` type itself, not just from the print sites, so a quote cannot come back without editing that type. The same cron also refreshes the conversation→order link (`link_social_conversations` RPC, skipped under `?preview=1`) — that is what keeps Софія seeing dialogs created since the last run.
- **Webhook registration is self-healing:** `/api/cron/telegram-webhook-sync` (every 15 min) compares getWebhookInfo against the desired URL + `allowed_updates` (incl. `business_*`) and re-registers on drift — a fresh bot token starts working within one tick, no manual step. `POST /api/chatbot/telegram/setup` (admin-only) remains as the immediate manual trigger. Helpers live in `lib/chatbot/telegram-business.ts`.
- **What leaves the inbox** (narrowed 2026-09-14, both paths). The watchdog and `/unanswered` used to quote 120 characters of the client's last message into the work chat; they now print only who is waiting and for how long. `lib/chatbot/client-chat-lookup.ts` used to search every message for a phone and then for a name, and fed up to 40 messages of whatever it found to the Anthropic API; it now reads only the dialog whose `order_id` matches, ignores links of confidence `name` entirely, and sends 15 messages. When no dialog is linked it returns `NO_DIALOG_LINE` — an explicit sentence, never an empty string, because a hole in the facts is exactly where the model invents (the same fix as the `клієнт НЕ лишив email` line). Access to the inbox itself is NOT the RLS policy (`is_admin_user()`, 4 emails) — the route reads with the service key behind `requireSection('ai','view')`, so every active staff member can read any dialog; narrowing that is a role-level decision (`ai: none`), not a code change.
- **Work group chats** (`lib/chatbot/work-commands.ts`): the bot in a group (or Diana's own private chat with it) is a control panel, never the customer AI. Registration is owner-gated (`/register`, owner = the Telegram Business account); after that any member can use `/status` (24h summary), `/order TM-…`, `/overdue`, `/unanswered`, `/chatid`. `/alerts_here` points team alerts at that group (settings `telegram_alerts_chat_id`; registered chats in `telegram_work_chat_ids`). The unanswered computation is shared between the cron and the command via `lib/chatbot/unanswered.ts`.
- **Софія cannot state an order fact without holding the order row** (2026-09-14, after a live failure). The router's last resort is `chatAboutLife`, a separate model call at temperature 0.8 that sees only recent chat lines and no order data. A question about TM-001314 whose number failed to parse landed there and produced an invented status, an invented deadline («15 січня» against a real 15.09) and an invented «склад укомплектований». The prompt already said «нічого не вигадуй про замовлення» and that did not hold, so the guard is now structural: `workGuardReply()` returns the order-number clarifier for anything matching `WORK_TOPIC` (замовлення/дедлайн/оплата/статус/склад/накладна/ТТН/номер) or anything number-shaped, in the message OR in the message it replies to, and it is checked both in the router and at the top of `chatAboutLife` — so no path reaches the model with a work topic. Small talk still works.
- **Order numbers are read in Cyrillic and in shorthand** (`extractOrderNumbers`, same date). «Тм-001314» typed with Cyrillic Т and м was invisible, and so was the team's «1314» — the old regexes took Latin prefixes only and a bare number of exactly five digits, always mapped to CRM. Now a homoglyph-normalised copy feeds the prefix match (Cyrillic Т/М/С/Р/В → Latin; «СРМ» normalises to CPM, which is accepted as CRM), and short forms — 4-digit «1314» and «001314» → `TM-001314` — are available per caller via `{ allowShortForms }`, requiring an order word within 30 characters before the number, or `{ assumeOrderContext }` when the message is a reply to Софія. They stay OFF for the silent mention capture, where four digits are usually a page count. Prices are still excluded by the currency check on the tail.
- **The reconcile queue is oldest-snapshot-first** (`orders.crm_reconciled_at`, 2026-09-14). `findSyncedOrders` used to order by `created_at desc` and take 25, so the same 25 newest orders were re-read every 30 minutes and everything below rank 25 was never reconciled again: of 131 site orders holding a CRM snapshot, 81 were older than a week and 16 older than a month, and 33 adopted cards had never been reconciled at all (they carry `payments_total`, written at adoption, but no `manager_name`, which only the reconcile writes). The queue now orders by `crm_reconciled_at asc nulls first, created_at desc`; the batch stays 25, so a full sweep takes about six runs (~3 hours) and load on KeyCRM is unchanged. The stamp is written on every successful pass — including when nothing changed, which is the fact that was missing — and also when the CRM answers that the card no longer exists, but NOT after a failed request, so a broken order stays at the head of the queue instead of silently rotating to the back. Orders in an active state (`ACTIVE_BEYOND_WINDOW`: new, confirmed, in_production, quality_check, ready, shipped) are now taken regardless of the 45-day window — three live orders were older than that and would never have been reconciled — while the window still keeps hundreds of finished cards out.
- **The KeyCRM stage is translated on DISPLAY, never in the mirror** (`lib/automation/crm-stage.ts`, 2026-09-14). KeyCRM returns its own built-in statuses under their internal keys and the team's own pipeline stages under their Ukrainian names — one map, two vocabularies — so 597 of 1011 cards showed the manager `completed` / `in_transit` / `waiting_for_prepayment`. `crmStageLabel(stage, siteLabel)` translates the five known keys, passes a Cyrillic name through untouched, and for an unknown key shows the site status with the key in brackets («підтверджене (CRM: returned)») plus a one-time console warning. It returns null when there is no stage at all, because 96 orders never reached the CRM and «Етап у KeyCRM: підтверджене» would be an invention; `stageOrStatus()` is the list-line variant that falls back to the site status. `custom_attributes.keycrm.status_label` still stores exactly what the CRM sent, and `status_id` is now stored beside it so a renamed stage cannot break the translation. **The four substring matchers stay as they are** — `statusFromCrm`, `isClosedCrmStage`, `fulfilmentFromLabel` and the risk-radar regex answer «what does this mean for the work», understand both vocabularies on purpose, and must not be routed through the dictionary. `SITE_STATUS_UA` also lives in that module now: it used to be two identical copies in work-questions.ts and work-commands.ts (the production-calendar page keeps its own capitalised labels deliberately).
- **Work-chat order mentions** (`lib/chatbot/work-chat-monitor.ts`): non-command group messages mentioning an order (TM-…/CRM-…/bare 5-digit KeyCRM id; numbers followed by грн/₴ are prices and skipped) are captured silently — an `order_history` note (`work_chat_note`/`work_chat_done`) + deadline TIGHTENED to any dd.MM date (earlier-only; completion reports never tighten). Completion attribution ladder: number in the message → number in the replied-to message → (done-reports only) the chat's last direct mention within 2h. Orders not yet mirrored from KeyCRM wait in `settings('work_chat_pending_mentions')` (48h TTL), drained every 15 min by the telegram-webhook-sync cron. Reactions: ✍ instruction / 👌 done — never a chat message. Needs the bot as group admin to see non-command messages.
- **Proactive team alerts** (all to the `/alerts_here` destination, falling back to Diana's chat with the bot): 💰 paid-order ping fired from the Monobank webhook on the first transition to paid (test orders excluded via `lib/automation/test-orders.ts`); ☀️ morning digest `/api/cron/work-chat-digest` (06:00 UTC) = deadlines only per Diana's 2026-08-11 format — overdue + due within `settings('digest_upcoming_days')` (default 3) + one dialogs line; 🌙 evening sign-off `/api/cron/work-chat-evening` (19:00 UTC) with the unanswered count and солодких снів; 🔔 unanswered-dialogs watchdog (see above). ## Pricing flow

Photobook prices are NOT hardcoded in the codebase. They live in Supabase, in the `photobook_prices` table (joined to `cover_types` and `photobook_sizes`). Three components work together:

1. **`app/api/pricing/photobook/route.ts`** — GET endpoint, server-side. Reads the full matrix (~466 rows) from Supabase, flattens it into a `{ cover_type, size, page_count, base_price, kalka_surcharge }` shape, returns JSON. Uses Next.js `revalidate = 60`, so price changes propagate to prod within 60s of a migration without redeploy.

2. **`lib/editor/usePrices.ts`** — client React hook (`usePhotobookPrices`). On mount, seeds state from `localStorage` (24h TTL) for instant first paint, then fetches `/api/pricing/photobook` in the background and updates state if anything changed. Returns `{ table, loading, error }`. Used by `BookLayoutEditor`, `EditorTopBar`, and the photobook product page.

3. **`lib/editor/pricing.ts`** — pure module. All exported functions (`lookupPrice`, `lookupPriceWithKalka`, `findPriceRow`, `calculateDynamicPrice`) take a `PriceTable` (or `null` for the fallback path) as their first argument. Knows nothing about React, fetch, or Supabase. Handles cover-type aliasing (`Velour` / `велюр` / `Velvet` → canonical `Велюр`), size normalisation (`20x30` → `20×30`), nearest-page-count fallback, and graceful null-table fallback to the price the user already saw.

**Why this shape:** the editor route uses `dynamic: 'force-dynamic'` + `ssr: false` (the editor needs browser APIs and is 200KB+), so a Server Component cannot pass prices in as a prop. Going through a thin API route lets us keep server-side caching while still letting the client refresh on its own schedule.

**Tracing paper ("калька") on the product page is not added to the displayed price** — the radio is intentionally lead-gen ("ціна уточнюється"). The editor, where kalka is part of the live config, does add the `kalka_surcharge` from the DB.

### Page-priced products (журнали + Travel Book) — and the drift check

Photobooks are priced from one table (`photobook_prices`) and have no second copy. The **page-priced** products do, and that is where price bugs keep coming from:

| Half | Where | Who prices from it |
|---|---|---|
| The scale — absolute ₴ per page count | `lib/products.ts` (`PHOTO_JOURNAL_SOFT`, `PHOTO_JOURNAL_HARD`, `TRAVEL_BOOK`) | конструктор (`BookConstructorConfig`), картка товару через `getCalculatedPrice` |
| База + надбавка за опцію | `products.price` + `products.options['Кількість сторінок'][].price` | сторінка товару (`ProductClient` Source 2/3) |

The two agree **only while `products.price` equals the cheapest tier of the scale.** Nothing enforced that, and on 2026-08 the hard-cover journal gained a 12-сторінковий tier at 675 ₴ while the column stayed at its old 825 ₴ — every configuration of that product went out exactly 150 ₴ over until TM-001202 was paid at 825 ₴ instead of 675 ₴.

**Migration to a single source is underway** (started 2026-08-19). `page_product_prices` (Supabase) holds the same 87 tiers as absolute prices — one row = slug × page_count × ₴, seeded by script from `lib/products.ts`, mirrored to the hryvnia at creation (SQL cross-check: 0 mismatches). `GET /api/pricing/page-products` serves it with the same 60s-revalidate contract as the photobook route. **Reads are NOT switched yet** — the site still prices from the old pair, while the audit now compares all THREE copies twice a day in the ops digest (`tableDrift` / `tableMissing` / `tableExtra` in the report). Switching reads (product page, selector, constructor, catalog cards) is the next step, only after several days of clean three-way audit.

Two things now hold it together:

- **`lib/pricing/audit.ts`** — pure; recomputes both halves for every tier of every page-priced product and reports each hryvnia of disagreement. When all tiers are off by the same amount it names the correct база, so the report is an instruction and not a list of symptoms. Read it from `GET /api/admin/pricing/audit` (staff-only) after any price change, and it runs inside the twice-daily **ops digest**, where drift is pinned above every order bucket.
- **`ProductClient`** derives `dynamicPrice` for journals from the scale on every options change (Travel Book already did). `products.price` is a display fallback, not the charged price.

- **`lib/pricing/final-price.ts`** — `computeFinalPrice()`: the product page's final price + labeled breakdown, extracted verbatim from `ProductClient` (2026-08-19) where it was ~150 untestable inline lines. Three sources by priority (photobook table → dynamicPrice → DB option modifiers), then percentage rush BEFORE flat extras. `getCalculatedPrice` and the inscription key are passed in / duplicated because their homes are `'use client'` modules — a test pins the key against `INSCRIPTION_KEYS.on`. `ProductClient` is now a thin caller; do NOT grow pricing arithmetic inside the component again.
- **`tests/pricing-*.test.ts` + `tests/final-price.test.ts`** — the only tests in the repo (Vitest, `npm test`, about one second). They pin every tier of every page-priced product as a literal, the order in which the rush multiplier and the flat extras are applied, the option predicates that read rush and lamination out of values/labels/locales, and the audit itself. Both halves are covered on purpose: `pricing-scales` is the price list written down, `pricing-composition` is what happens when the customer also picks rush, lamination and typesetting — the layer where every historical bug actually lived. Verified by mutation: reverting the string-page-count fix fails 6 tests, moving one tariff by 5 ₴ fails 3.

**Adding a product to the audit:** append it to `PAGE_PRICED_PRODUCTS` in `lib/pricing/audit.ts` with its scale from `lib/products.ts`. Do NOT add photobooks — they have no second copy to drift from, and a hardcoded photobook table here would recreate the bug the audit exists to catch.

**Known gap:** the hard journal is sold in 4-page steps (12, 16, 20…) while its twin Travel Book is sold in 2-page steps (12, 14, 16…) off the identical 75 ₴ scale. A hard journal built to 14 pages in the editor rounds up to the 16-page price — the same "paid for 24, received 22" class as TM-001195. Filling in the odd tiers is a product decision for Diana, not a code fix.

**Historical note:** Until 2026-05-14, `pricing.ts` shipped a hardcoded ~150-row table. The table drifted from the DB — `velour_20×30` was missing entirely, so the editor showed 1200₴ instead of 1985₴ for velour 20×30 / 10pp / +kalka. The hardcoded table has been removed; the DB is now the single source of truth.

## Payment flow & designer handoff

The end-to-end path from cart to designer brief:

1. **Cart → checkout.** The `/cart` page is now **navigation-only** — it lists items and totals and its button routes to `/[locale]/checkout`. It no longer collects contact/delivery or creates orders (the old `/cart` "Pay" button POSTed to a deleted `/api/checkout/create-invoice` and 404'd, blocking all online payment). `/checkout` is the single online entry point: it owns the contact → shipping → payment steps, calls `/api/orders/submit` (which resolves `payment_mode` and may downgrade split→full), then `/api/monobank/create-invoice`. It also runs `linkPendingExports` — reading each `sessionStorage.export_{cartItemId}` descriptor that constructors stash and inserting `order_files` rows — **before** `clearCart()`, so designed files (photobook PDFs, posters, star maps) always attach to the order. `lib/submitOrder.ts` inserts the `orders` row with `payment_status='pending'`, `order_status='new'`; line items go into `orders.items` JSONB.

2. **Invoice creation.** Customer hits "Pay" → POST `/api/monobank/create-invoice` with `{orderId, paymentRegion: 'ua'|'international'}`. The token is now taken from the active `bank_accounts` row whose `region` matches the destination (UA → ФОП Коблик, international → ФОП Гоголь); env tokens (`MONOBANK_TOKEN` / `MONOBANK_TOKEN_INTL`) are only a fallback if the DB row is missing. The charged amount is `order.total` (already the marked-up UAH — see "Region pricing" below), or `prepaid_amount` for a 50/50 split. Stores `monobank_invoice_id` + `monobank_payment_url`, logs to `order_history`, returns the page URL. Always charges in UAH (`ccy: 980`); foreign cards are converted by the customer's own bank.

3. **Customer pays on Monobank.** Monobank fires a webhook to `/api/monobank/webhook` (canonical path). Two legacy aliases — `/api/webhook/monobank` and `/api/webhooks/monobank` — re-export the canonical handler, so Monobank can hit any of the three URLs without breaking.

4. **Webhook handler** (`app/api/monobank/webhook/route.ts`) does, in order:
   - Verify the `X-Sign` signature with `MONOBANK_PUB_KEY`. Production webhooks without a configured pub key return 503 to avoid silently accepting unsigned payloads.
   - Look up the order, sanity-check that `amount` matches `total * 100` ± 1 kopeck (defence in depth).
   - Atomic conditional UPDATE on `orders` setting `payment_status`, `monobank_invoice_status` etc, through the `apply_monobank_payment()` SQL function (a direct PostgREST update breaks whenever the schema cache goes stale on `monobank_invoice_id`). It writes only when the (invoice id, invoice status) tuple is new, and returns the order id only to the caller that won that race — concurrent deliveries can't both insert duplicate history rows.
   - **Stage order: a later state is never overwritten by an earlier one (2026-09-14).** Monobank does not guarantee delivery order, and "the tuple is new" said nothing about *direction*: on TM-001087 a `processing` event landed 47 ms after `success`, differed from it, passed the guard, and wrote `payment_status` back to `pending` — a paid order reading unpaid, with the money-red badge and a place in «Потребує уваги». `paid_at` survived only because it alone was written conditionally, which is what made the damage visible. The race hit 7 orders; 4 still carried a stale stage and 1 a stale payment status when this was fixed. `mono_stage_rank()` now ranks the lifecycle — `created` 10, `processing` 20, `hold` 30, `expired`/`failure` 35, `success` 40, `reversed` 50, anything unknown or NULL 0 — and the UPDATE's WHERE applies an event only if its rank is not lower than the stored stage's. Two things about that table are load-bearing. `reversed` sits ABOVE `success` because a refund legitimately follows a payment and must apply. `failure` and `expired` sit BELOW `success` rather than beside it: on equal ranks a `failure` arriving after `success` would pass a "not lower" test and mark a paid order failed — the same defect mirrored — so on top of the ranks there is an explicit rule that **once the stored stage is `success`, nothing applies except `reversed`**. A DIFFERENT invoice id skips the rank check entirely and is its own branch of the WHERE: a re-issued payment link starts at `created` (rank 10) and comparing that against the old invoice's `success` would reject every event of the new attempt. Migration `20260914_monobank_stage_order.sql`, which also repaired the four historical rows (the amount on TM-001087 is a reconstruction — see the migration header for what each value rests on). The rule lives only in SQL and has no vitest twin on purpose: a TS copy would be the drift risk, not the safety net — exactly how the two copies of the paid-in-full rule drifted apart and had to be stitched back together by a test. It is tested where it lives instead, by `supabase/tests/monobank_stage_order.test.sql`: a read-only `do $$ … $$` block that raises on the first mismatch, covering the rank ORDER (not the literal numbers, so the gaps stay re-spaceable) plus every lifecycle transition worth asserting. Run it in the Supabase SQL editor or via `psql`; it touches no tables and is safe on production. `npm test` does NOT run it — vitest cannot see Supabase — so run it by hand after any change to either function. **Anything that confirms a payment must also write the stage it is confirming**, or it disarms that guard on exactly the orders it just fixed: an order left at `created` (rank 10) accepts a late `failure` (rank 35) and flips a paid order to failed. `check-payment` writes the stage it read from the bank (`ff3d379f`); `mark-paid` writes `success` **only when the order carries a `monobank_invoice_id`** (`20260914_mark_paid_invoice_stage`) — that button is also used for money that never went through Monobank at all (cash, transfer, COD), and stamping a bank-invoice stage on those would be inventing an event that never happened.
   - **Claim the paid transition (2026-09-13).** `paid_at` is NOT set by that function any more (`p_set_paid_at` is always false). Instead, on `success` the handler runs one guarded UPDATE — `set paid_at = now() where id = ? and paid_at is null` — and EVERY once-per-order side effect below hangs on whether it returned a row. Before this they all asked `existingOrder.payment_status !== 'paid'`, a snapshot read at the top of the request: stale by the time it was used, so a manual «Позначити оплаченим» landing in between, or a second webhook for the same invoice with a different status, made two callers each decide they were the first and each send the paid email. The condition now lives in the UPDATE's WHERE, where only one caller can win it. The side effects are: stock deduction, the paid email, the work-chat ping, referral reward, agency commission, certificate redemption, babybook start, production automation, fiscalisation, print render, designer handoff, certificate issue.
   - Insert into `order_history` with the human-readable note.
   - On `success`: auto-confirm the order if it was still `new`.
   - The paid email is sent from ONE place in this handler. A second fire-and-forget POST of `{action:'paid'}` used to sit ~140 lines further down under its own copy of the stale guard, so a customer could get two identical letters about one payment; it was removed 2026-09-13 and the awaited call next to the stock deduction is the only one left.
   - On `success` AND `with_designer=true` AND the claim won: fire-and-forget POST `/api/designer-service/on-payment`. The Monobank webhook is not allowed to block on email + Telegram (those would make Monobank retry the webhook on slow APIs), so we don't await.

5. **Designer handoff** (`app/api/designer-service/on-payment/route.ts`):
   - Loads the order + customer (joined customers row, or inline `customer_*` fields for guest checkout).
   - Creates a `design_briefs` row with `status='waiting_brief'`. Token is generated by the `gen_brief_token()` Postgres DEFAULT — server-side capability that the customer can later use to access their brief form without logging in.
   - Sends the brief link email via Brevo (`sendBriefLinkEmail`). Skips silently if no email is on file.
   - Pings the designer Telegram chat with the order summary + brief token.
   - Idempotent: re-running on the same order finds the existing brief and just re-sends the email.

6. **Customer fills the brief.** Hits `/api/designer-service/brief/[token]`, fills the form (occasion, style, photo order, important_photos, title_text, additional_notes), uploads photos to the `design-briefs` storage bucket. `submitBrief()` updates the row to `status='brief_received'`, then `triggerAIProcessing()` fires off the AI photo analysis in the background.

7. **Designer picks up the order** in `app/admin/designer/`, assigns themselves (`orders.designer_id` + `assigned_at`), opens the brief, builds the book in the editor.

8. **Revision round-trip.** Designer hits "Send for review" → creates a `design_revisions` row with its own `client_token`, emails customer the review link. Customer approves or asks for changes (`client_decision` + `client_comments` + `general_feedback`). `revision_count` increments per round; the contract caps at 3.

### Region pricing, currency & ship region

Canonical price is **always UAH**. Two checkout decisions depend on (interface language) × (delivery destination), and both live in one pure module, `lib/payment/pricing-region.ts`, used by the server (authoritative) and the client (display) so "shown == charged":

- **`resolvePriceMultiplier(locale, shipRegion)`** — the international markup (×1.30) applies ONLY at `locale !== 'uk' && shipRegion === 'INTL'`. The markup is a function of locale × shipRegion, **not** of currency. `convertPrice` in `lib/i18n/currency.ts` is now a pure conversion (markup was decoupled from it); storefront cards apply markup via `formatDisplayPrice(...)` using the locale's `defaultShipRegion`.
- **`resolveDisplayCurrency(locale, userChoice)`** — default UAH for uk, EUR otherwise; checkout has a UAH/EUR switcher available to everyone. Display only — charge is always UAH.

**International shipping** is a flat €25 fee (free-shipping disabled — config `free_threshold_eur` = 0; set it > 0 to re-enable a free-over-threshold tier) (`computeIntlShippingUah`, config in `settings('intl_shipping')` = `{free_threshold_eur, flat_fee_eur}`, defaults in `DEFAULT_INTL_SHIPPING`). The threshold/fee are in EUR; the order's marked UAH subtotal is converted via the buffered rate to decide. `/api/orders/submit` computes the fee server-side and stores it in `orders.delivery_cost`; the checkout fetches `/api/exchange-rate` (public: rate + threshold + fee) so its displayed total and free-shipping nudge match the charge exactly. Recipient-pays-on-delivery is **not** available for outbound international (domestic-only), so intl shipping is always prepaid in the order total. NOTE: a uk-locale customer shipping abroad gets no markup (matrix: base UAH) but pays the same flat €25 shipping — fine.

The checkout shipping step now carries an authoritative **UA / INTL selector** (`shipRegionChoice`) that drives the address form (Nova Poshta picker vs free international address), the payment account, the markup, split availability (INTL = full prepayment only, enforced server-side in `/api/orders/submit`), and the currency default. The old late "payment region" modal was removed.

`/api/orders/submit` receives base UAH `subtotal`/`total` + `ship_region` + `locale` + `display_currency`, applies the multiplier itself (a tampered client can't skip it), and **freezes** `ship_region`, `price_multiplier`, `display_currency`, `exchange_rate` on the order.

**EUR rate** lives in `settings('eur_rate')` (`{rate, base_rate, buffer_pct, source, updated_at}`), read server-side via `lib/i18n/exchangeRate.ts` (cached). It's refreshed twice a month (1st & 15th, `0 5 1,15 * *`) by `/api/cron/update-exchange-rate` from the NBU official rate with a margin buffer — predictable price-change dates rather than daily drift.



### Manual order create (parallel entry point)

The Monobank webhook is the path for orders the customer pays online. Most of Diana's real volume comes through Instagram DM, where an admin enters the order by hand in `app/admin/orders/create`. That route (`/api/admin/orders/create`) mirrors the webhook side effects so manually-created orders aren't second-class:

- Inserts an `order_created` row in `order_history` with the source (`manual` / `instagram` / etc.) and `created_by` FK, so the order detail page's history feed shows when and how the order entered the system.
- If `with_designer=true` AND the admin marks the order paid on the form, fires the same `POST /api/designer-service/on-payment` the webhook does — fire-and-forget, no await, downstream is idempotent.

Both entry points converge on the same designer-handoff route, so the brief creation / email / Telegram ping logic lives in one place (`app/api/designer-service/on-payment/route.ts`) regardless of how the order was paid.

The three webhook endpoints, the dual `mono_*` / `monobank_*` order columns, and the historical reference to `design_orders` / `designer_assignments` in earlier drafts of this doc are all artefacts of the same migration episode and have been straightened out — `monobank_*` is canonical, the older alias columns are dead code paths preserved only because dropping them is a DB migration risk for very little gain.

## Partner referral program (travel agencies, bloggers, photographers)

One program, four kinds of partner (`agency_partners.partner_kind`: `travel_agency`, `wedding_agency`, `travel_blogger`, `photographer`). Do not confuse it with the two neighbours: the **friend referral** (`referrals` + bonus balance, `/api/referral/*`) is a customer-to-customer mechanic, and **wedding agencies** at `/wedding-agencies` are a plain B2B discount on `customers.b2b_*` with no commission ledger.

**Flow.** Application (`/partnery/apply` → `partnership_requests`, or a manager's `/api/sales/partner-requests` → `partner_activation_requests`) → manual approval → one `agency_partners` row plus one `promo_codes` row carrying the **same code string** → welcome email with `?ref=CODE` and the cabinet link → visitor lands, `ReferralCapture` stashes the code in `localStorage` → checkout auto-applies it via `/api/promo/validate` → `orders.promo_code` → on the paid transition `processAgencyCommission` writes one `agency_commissions` row → partner cabinet → payout.

**The model is "link only + lifetime binding" (Diana, 2026-09-16).** A client reaches the shop through `?ref=` and the 5% comes off by itself; the code is never shown to them and typing it by hand is refused (`/api/promo/validate` answers "цей код працює лише за посиланням партнера" for any code that belongs to `agency_partners` and did not arrive with `source:'link'`). The welcome email and the partner cabinet show the LINK only — the code survives as an internal identifier visible in the admin. Ordinary promo codes (WELCOME7 and friends) are untouched by any of this.

The **first paid order** with partner attribution binds that buyer's normalised email to the partner forever, in `partner_client_bindings`. From then on EVERY paid order from that email earns the partner 5%/3%, with no link click, no localStorage and no account — the binding is created once and a later click on someone else's link never overwrites it (the email is the primary key, so the rule is enforced by the database rather than by a check that would lose a race between two simultaneous payments). The **discount is not lifetime**: 5% applies only to that first, binding order, and repeat orders are full price with no mention of a partner in the client's UI. Ordinary promo codes work freely on repeat orders and do not block the commission. The 90-day localStorage window governs only the path BEFORE binding; afterwards the email decides and localStorage is irrelevant.

**The binding and the ledger row are written by ONE database transaction** (`record_agency_commission`, migration `20260916_binding_requires_commission.sql`). They used to be two separate calls with the `totalCommission > 0` check sitting between them, which meant any order whose item shape the reader did not recognise left a half-state that nothing repairs: the buyer bound to the partner forever, and no money for the partner, their sales manager, or the ledger. That is not hypothetical — the designer flow writing `price` instead of `unit_price` would have produced exactly it on TM-001326. There is deliberately **no standalone function that creates a binding** any more; `lib/agency/binding.ts` only reads.

**Commission of zero has two meanings, and they are told apart by `orders.subtotal`, not by the item shape.** Enumerating known price field names is the patch that already failed once, since the next unknown name is unknown by definition. Instead `classifyItemsSubtotal` compares the summed items against the order's own subtotal, written by the same flow but separately from the items: an order that says 675 ₴ while its items read as 0 has broken items, whatever their shape. A shortfall beyond **1%** (`ITEMS_SUBTOTAL_TOLERANCE`) refuses everything — no manager accrual, no binding, no commission — and logs loudly, because a refusal is visible and re-runnable while an under-paid ledger row is silent and frozen by `UNIQUE(order_id)`. The threshold discards nothing that exists today: across 815 paid orders the item sum was never *below* subtotal, 763 matched to the kopeck, and the 52 that differed are all KeyCRM mirrors where the item sum is 3–8% *above* subtotal because the CRM discount sits on the order. A **legitimately** zero commission — a partner on 0% rates, or a genuinely free order — still creates the binding and simply writes no ledger row: the client is real and their next order should earn.

Commission attribution therefore lives in **`orders.referral_partner_id`, not `orders.promo_code`** — the client can type a normal promo over a partner link, or dismiss the partner discount entirely, and the partner still earns. `processAgencyCommission` resolves the partner from that column, then from the binding, then (for pre-existing orders and manual admin entry) from the legacy promo code. Ledger rows carry `kind`: `new_client` for the order that created the binding, `repeat` for everything after, which is what the cabinet splits into separate figures. All the earlier rules still apply to repeat accruals — cancellation reverses only PENDING commissions, self-referral (buyer email == partner email) earns nothing AND creates no binding, `UNIQUE(order_id)` keeps it idempotent, and totals come from `recalc_agency_partner_totals()`.

**One code, two jobs.** The same string is the client's discount (`promo_codes`) and the partner's attribution key (`orders.promo_code`). Both must line up, and since 2026-09-16 they are forced to: `orders/submit` derives `promo_code` from `promo_codes` **by `promo_id`**, never from the request body. Trusting the body meant a request could name a partner's code with no `promo_id` at all — no discount applied, no check triggered, and the partner credited after payment.

**The partner welcome email exists once**, in `lib/agency/welcome-email.ts` (`buildPartnerWelcomeEmail` / `sendPartnerWelcomeEmail`, sent through Brevo, never throws). `POST /api/admin/agency-partners/[id]/resend-welcome` — the admin "Надіслати лист" button — used to carry a full second copy inline, and it had drifted on four counts: it led with the CODE instead of the link, hardcoded the client discount to 5 instead of reading the partner's promo row, knew two of the four partner kinds (a photographer was called "агенцією"), and never mentioned the lifetime binding. A partner re-sent the email therefore read different terms than one who got it at approval. `tests/partner-welcome-email.test.ts` pins all four so the copy cannot come back unnoticed.

**Partner email is normalised inside `createAgencyPartner`** (trimmed, lower-cased, via the same `normalizeBindingEmail` the client binding uses) and an unusable one throws rather than creating a half-dead partner. It used to be each caller's job and only two of the four did it — the admin flow took the address straight from the request body and the photographer cabinet from `photographers.email`. Case never mattered, since every read is an `ilike`; a stray space did, and silently on both sides: `/uk/partner/cabinet` would say "cabinet not found" and the recovery form would answer "sent" while sending nothing. `20260916_normalize_partner_emails.sql` cleaned the existing rows (0 of 3 needed it — insurance, not a cure).

**Partner creation goes through `lib/agency/create-partner.ts` and nowhere else.** The admin approval route, the manager-request approval and the photographer cabinet all call it. It used to be duplicated in `/api/admin/agency-partners` and the copy drifted (no duplicate-email guard, only two of four kinds, wrong wording in the promo note). Code uniqueness is checked in **both** `agency_partners` and `promo_codes` — both carry a unique index, and checking one alone made the other fail with a raw Postgres error.

**Commission rules (Diana, 2026-09-16).** Base is the subtotal **before** the client discount — `total_price` per item, since the discount lives in `orders.subtotal − orders.total` and is never split across items. A **self-referral** (buyer email equals partner email) gets the discount but no commission, and no manager accrual either; the check is inside `processAgencyCommission` because five call sites reach it. Attribution from a stored `?ref=` expires after **90 days** (`REF_ATTRIBUTION_TTL_MS` in `lib/referral/pending-code.ts`); a fresh `?ref=` in the URL is always honoured. On cancellation, `reverseAgencyCommission` flips a **pending** row to `payout_status='cancelled'` — already-paid commissions are left alone on purpose.

**Totals are derived, not accumulated.** `agency_partners.total_earned` / `total_paid_out` are recomputed from the ledger by `recalc_agency_partner_totals(uuid)` (called from inside `record_agency_commission`, in the same transaction as the insert), and per-agency aggregates come from `agency_commission_stats()` (both in `supabase/migrations/20260916_agency_commission_integrity.sql`). Read-modify-write on those columns lost updates under concurrent webhooks, and summing the ledger in JavaScript was an unpaginated read straight into gotcha 14.

**Files.** `lib/agency/{create-partner,commission,welcome-email}.ts`, `lib/sales/{commission,attribution,partner-activation}.ts`, `lib/referral/{pending-code,promo-code}.ts`, `components/ReferralCapture.tsx`, `app/[locale]/partnery/*`, `app/[locale]/partnerska-programa-dlya-{blogeriv,turagentstv}/*`, `components/partners/*`, `lib/partners/landing-content.ts`, `app/[locale]/partner/*`, `app/api/partnership/*`, `app/api/admin/{agency-partners,partner-requests,partnership-requests}/*`.

**Three ways into the partner cabinet, and only one of them is a password.** The cabinet is opened by `cabinet_token` alone — a random UUID that exposes earnings and payout bank details — so every route into it ends at the partner's own mailbox.
1. The welcome email at approval carries the token link.
2. `/uk/partner/cabinet` resolves it from a **logged-in account**: `GET /api/partnership/my-cabinet` reads the session with the cookie-bound client, lower-cases `user.email` and matches `agency_partners.email` with `ilike` + `likeEscape` (case-insensitive exact). Partners have no password of their own — this is an ordinary site account on the same address, and Supabase enforces email confirmation, so registering on someone's partner address does not get you in without their mailbox (1325 accounts, 45 unconfirmed, none of which has ever signed in).
3. `/uk/partner/find` → `POST /api/partnership/find-cabinet` mails the link to a partner who has neither the email nor a matching account.

**The find form is built around what it must not reveal** (`lib/partners/find-cabinet.ts`). The on-screen answer is byte-identical for every outcome — found, unknown, suspended — and the status is always `200`, because differing status codes would leak exactly what the wording hides; otherwise the form would be an enumerable directory of who partners with touch.memories. The link never reaches the screen, only the mailbox. The recipient comes from `partner.email` in the database, never from the submitted address, which is what `decideCabinetRecovery` exists to make testable: that rule must survive any future widening of the lookup. Suspended partners get the same silence, since their promo code is already switched off and a working cabinet would be a promise the system does not keep. Limits are **5 per hour per IP** plus a **15-minute cooldown per mailbox** — the IP limit alone protects nothing, because addresses are plentiful and the mailbox is one. Every send writes `email_logs` with `template: 'partner_cabinet_recovery'`, which is the only place to check delivery precisely because the screen says nothing. Known and deliberate limit: the reply is constant but the *timing* is not, since a match still calls Brevo; at five attempts an hour, timing enumeration is impractical, and moving the send outside the request would break on serverless.

**Sales-manager commissions mirror the partner ones, and since 2026-09-16 they actually do.** A manager earns `rate_order` (1% by default) of every order their partner brings and `rate_gallery` (5%) of every gallery plan their photographer pays for; the order accrual runs inside `processAgencyCommission`, so it fires on the same paid transition from the same five call sites. Two halves of that mirror were missing and both were silent:
- **Cancelling an order now reverses the manager's row too** (`reverseSalesCommission`, wired into `PATCH /api/admin/orders/[id]` and the unpaid-orders cron right beside `reverseAgencyCommission`). Only the partner side was reversed before, so a cancelled order kept paying the manager. It flips `pending → cancelled` on `kind='order'` rows only — a gallery accrual has its own `source_id` and must not be caught by an id collision — leaves `paid` rows alone on purpose, and is idempotent because the status condition sits in the UPDATE.
- **`sales_managers.total_earned` / `total_paid` are derived, not accumulated**, via `recalc_sales_manager_totals(uuid)` (`20260916_sales_manager_totals.sql`), the exact counterpart of `recalc_agency_partner_totals`. `total_earned` was read-modify-write, which loses an accrual when two webhooks land together, and the admin status switch adjusted `total_paid` by a delta while never touching `total_earned` at all — so a cancelled row still counted as earned. One function now brings both columns to whatever the ledger says.

`cancelled` is excluded from money everywhere: the recalc skips it, `/api/sales/me` no longer sums it into «Зароблено всього» (it used to sum every row while the two neighbouring cards filtered by status), and the cabinet labels such a row «знято, замовлення скасовано» instead of showing it as awaiting payout. The row itself stays visible — same rule as the partner ledger.

**The manager cabinet shares the public link and never the private one.** Each row in «Мої партнери» shows `partnerRefLink(code)` with a copy button and a ready Ukrainian DM text (`lib/partners/share-message.ts`) stating the real terms: the discount applies to the client's FIRST order, the partner's percentage applies to every order forever. The partner's `cabinet_token` is not shown, and the boundary is held server-side — `/api/sales/me` does not select the column at all.

**Known gaps, recorded rather than fixed (Diana, 2026-09-16).** The duplicate-email guard in `/api/admin/agency-partners` uses `.maybeSingle()`, which errors instead of returning a row if two partners ever share an address. And `/api/partnership/my-cabinet` silently takes the newest row (`order created_at desc`, `limit 1`) when one email has two partner records. Both need a product decision about what two partners on one address should even mean.

**RLS.** `agency_partners`, `agency_commissions` and `partner_activation_requests` have RLS on with **zero policies** — deny-all for anon/authenticated, reachable only through the service-role client in API routes. That is deliberate; do not "fix" it by adding a read policy.

**Link clicks (added 2026-09-16).** `referral_visits` records one row per click-through: `referral_code`, `landing_path`, `created_at`, and deliberately **nothing else** — no IP, no User-Agent, no visitor id, no link to `customers`. A row says "this code was opened then, onto that page", which is all a partner needs and is one fewer table holding personal data. It has **no FK to `agency_partners`** on purpose: counting by code over `referral_visits_code_created_idx` is just as fast, and every new foreign key is another place gotcha 12 can fire. Codes are stored upper-case (normalised on both sides) so the match is a plain `=`.

A visit is counted **only when the code arrives as `?ref=` in the URL** — the later pages a visitor browses carry no parameter and are not clicks, otherwise the number would measure browsing depth instead. Repeat opens of the same link inside 24 h count once (`VISIT_DEDUP_WINDOW_MS`), remembered in the visitor's own `localStorage`; the server adds a short in-memory guard keyed on IP+code that is never written anywhere. The rule is `lib/referral/visit.ts` (pure, tested in `tests/referral-visit.test.ts`), the write path is `POST /api/referral/visit` (fired by `ReferralCapture`, always answers 200 so it never becomes an oracle for which codes exist, and only stores a code belonging to an ACTIVE partner). A headless browser with no `localStorage` can still inflate the count, which is why the cabinet shows visits next to paid orders and a conversion figure rather than as a number on its own.

Counting goes through `referral_visit_stats()` from the same migration, never a row fetch: this table fills from shop traffic and grows faster than any of gotcha 14's six, so summing it in JavaScript would hit the silent 1000-row ceiling. RLS on, zero policies, same as the rest of the program.

## Photographer galleries (added 2026-09-24)

A photographer's client galleries: the cabinet at `/[locale]/photographer/cabinet/[token]` (auth is the cabinet token, not Supabase Auth) and the public page behind `photographer_galleries.client_token` (`GET /api/gallery/[token]`). Not to be confused with the photographer as a **partner** in the referral program above — same person, separate tables.

**Tables.** `photographer_galleries` is one row per shoot: `expires_at` (term 30/60/90 days, extendable up to `MAX_TERM_DAYS`), `files_purged_at`, `cover_photo_id`, `design`, `zip_downloads`. `photographer_gallery_photos` is one row per file: `storage_path`, `storage_provider`, `size_bytes`, `media_type` (`photo`/`video`), `favorite`, `download_count`. There are **two FKs between these tables** (`gallery_id` and `cover_photo_id`), so an embed must be hinted: `photographer_gallery_photos!gallery_id(count)` (gotcha 12).

**Where the files live.** `lib/photographers/storage.ts` is the only door. New uploads go to Cloudflare R2 when the five `R2_*` env vars look real (`isR2Configured()`), otherwise to the Supabase bucket `photographer-galleries`. Each row records its own `storage_provider` and every read resolves the URL from it, so a mixed gallery works and nothing is ever migrated. R2 exists because Supabase egress is what made galleries expensive. The path is always `{photographer_id}/{gallery_id}/{timestamp}_{name}` (`galleryPhotoPath`), which is also the only way to find a file whose row is gone. `/api/photographers/storage-check` does a write–head–read–delete round trip and says why R2 is off.

**Uploads.** Small photos go multipart through `POST /api/photographers/galleries/[id]/photos`. Anything above ~4 MB and every video goes **sign → confirm** through `/api/photographers/galleries/[id]/videos`: `sign` checks size, file count and quota, then mints a single-use upload URL for one path; the browser PUTs straight to storage; `confirm` checks the path belongs to this photographer and gallery, asks storage whether the object exists and how big it is (never trusts the client), and only then inserts the row. Limits are in `lib/photographers/helpers.ts`: **2000 files per gallery** (`MAX_PHOTOS_PER_GALLERY`), 100 MB per photo, 2 GB per video.

**Quotas.** `lib/photographers/plans.ts` gives 4 / 50 / 250 / 500 GB (Безкоштовно / Старт / Про / Студія). An expired paid plan counts as free (`effectivePlanId`), and `photographers.storage_limit_mb` overrides the plan's cap. `lib/photographers/usage.ts` sums `size_bytes` over the photographer's rows page by page. `checkQuota` runs per file BEFORE anything reaches storage and answers 402 so the cabinet opens the upgrade dialog.

**Reading rows.** One gallery alone can pass PostgREST's silent 1000-row cap, so every «all photos of these galleries» read goes through `lib/photographers/gallery-photos.ts`: `.range()` pages of 1000 ordered by `(created_at, id)`, any page error fails the whole read, and more than 10 pages is an error rather than an endless loop. The table is in `WATCHED_TABLES` of `scripts/unpaginated-queries.mjs` (gotcha 14).

**Retention cron** (`/api/cron/cleanup-galleries`, daily 03:30 UTC; logic in `lib/photographers/gallery-cleanup.ts`, tested in `tests/gallery-cleanup.test.ts`). It guarantees that **a row disappears only after storage confirmed its file is gone**:
1. read ALL rows of the expired gallery through the helper;
2. `removeFiles()` — returns `null` only when every file is gone; R2 keys while R2 is off, a non-empty `Errors` in a `DeleteObjects` 200, or a Supabase path that `remove()` skipped and that still exists are all errors;
3. only then delete rows **by their ids** (never `eq('gallery_id')`, which would take a row uploaded mid-purge whose file nobody deleted);
4. recount with `head: true`, and set `files_purged_at` only at 0.

Any failed step leaves the gallery for the next night and lands in `skipped` with its stage; one bad gallery never aborts the run. It purges up to 25 galleries out of a window of 200 candidates, so stuck galleries cannot starve the rest (gotcha 13), and stops starting new ones after 45 s. Before 2026-09-24 it read one unpaginated page and deleted every row, so files past the 1000th would have stayed in R2 with no row; `scripts/r2-orphans-purged-galleries.mjs` (read-only) counts what may be left under purged galleries' prefixes. Deleting a single photo in the cabinet follows the same rule: storage failure → 502 and the row stays.

**Letters to the photographer** (added 2026-09-25; `lib/photographers/notices.ts`, rules in `notice-rules.ts`, texts in `notice-emails.ts`, tests in `tests/photographer-notices.test.ts`). Three, all through `sendLoggedEmail`, each exactly once per event, the «sent» mark set only after the provider accepted it, and none of them can fail an upload or a purge:
- **«галерея скоро згасне»** — the retention cron, before purging. Sent on the last nightly run after which fewer than three days would remain, so the photographer always gets 3–4 days, not 2–3. The mark is `expiry_notice_for` = the `expires_at` the letter was about, so an extension re-arms it without any code in the extension routes.
- **«місце закінчується»** — after the row is inserted in both upload routes (multipart `photos` once per request, `videos` confirm once per file). 90% by `getStorageUsage`; `storage_notice_sent_at` re-arms when usage before or after the upload is under 80%. Parallel confirms are serialised by the `storage_notice_pending_at` lease (5 min).
- **«файли галереї видалено»** — the retention cron, after purging, only for galleries whose `files_purged_at` is set; a failed send is retried on the next nights for three days, which also keeps galleries purged before this existed out of it.
The letters greet with a plain «Доброго дня!» (no automatic vocative). A test copy of all three goes out through `GET /api/admin/photographers/notice-test` (template suffix `_test`, no marks set). The demo cabinet (`DEMO_PHOTOGRAPHER_EMAIL`) and inactive cabinets are skipped. The new columns carry no foreign keys, so no embed changes (gotcha 12). Senders overview: `docs/email-senders.md`.

## Routing & i18n

- All public routes live under `app/[locale]/` — locale is one of `uk`, `en`, `ro`, `pl`, `de`
- Default locale: `uk`
- Middleware handles locale detection and redirects — it is **`proxy.ts` in the repo root, and there is no `middleware.ts`**: Next.js 16 renamed the file, the build log prints it as `ƒ Proxy (Middleware)`, and a search for `middleware.ts` finds only the unrelated `lib/supabase/middleware.ts` helper. It puts the locale prefix on any path that arrives without one (cookie `tm_locale` → `Accept-Language` → `uk`), carries the whole query string across, and sets `tm_locale` — which is why a link like `/unsubscribe?token=…` works and lands on `/uk/unsubscribe?token=…`
- Static labels: `locales/{locale}.json` files, accessed via the `useT()` hook
- DB-driven content (product names, category names, footer sections etc.) uses a `translations` JSONB column with shape `{ uk: {...}, en: {...}, ro: {...}, pl: {...}, de: {...} }`
- The `getLocalized(record, field, locale)` helper in `lib/i18n/localize.ts` reads `translations[locale].field || record.field` (fallback to base column)

## Blog (added 2026-09-22)

Posts live in Supabase `blog_posts` (+ `blog_categories`), never in MDX or files. The base row is Ukrainian; other locales live in its `translations` JSONB, and `locale` names the base language.

### Publishing is a queue, not a flag

A post is in exactly one of three states, held in `blog_posts.status`:

| status | Meaning | Visible? |
|---|---|---|
| `draft` | Being written | no |
| `scheduled` | In the queue, carries `publish_at` | no — **only the cron opens it** |
| `published` | Live, carries `published_at` | yes |

`/api/cron/blog-publish` (Vercel cron, `0 5 * * *` = 07:00 Kyiv in winter, 08:00 in summer — Vercel schedules in UTC only) takes the single oldest `scheduled` post whose `publish_at` has passed, flips it to `published`, revalidates the article/list/category/home/sitemap paths, and pings IndexNow. **One post per run on purpose**: after an outage, opening every overdue post at once would dump three or four articles into the feed and the RSS in one morning.

Three fields decide visibility together — `status`, `is_published`, `published_at` — and `lib/blog/published.ts` checks all three. A post with the flag but no `status` is invisible with no error anywhere, which is why every write goes through `lib/blog/queue.ts` (cron, admin buttons, generator) rather than a hand-written `update`. `lib/blog/queue.ts` is also the **only** file outside `/admin/` allowed to read `blog_posts` past that gate, and `tests/blog-schedule.test.ts` enforces that for the rest of the repo.

Scheduling lives in `lib/blog/schedule.ts`: gaps alternate 2 and 3 days at 07:00 Kyiv, computed through `Intl` rather than a hardcoded offset, because Kyiv is UTC+2 in winter and UTC+3 in summer.

### The queue going empty is silent, so it is watched

Nothing breaks when the queue runs dry — the site works, articles just stop. The cron writes `settings.blog_queue_watch` on **every** run (a watchdog that is quiet and a watchdog nobody ran look identical), the admin list shows that row in its header via `/api/admin/blog/queue-status`, and an email goes to the shop inbox when the queue is at three or fewer, at most once a day. That email is to ourselves, so it goes through `sendEmail` and deliberately not through `sendLoggedEmail` (gotcha 20 in CLAUDE.md).

New admin columns must also be added to the `blog_posts` allowlist in `lib/admin/content-tables.ts` — `/api/admin/content` rejects the whole request on an unlisted field rather than dropping it.

### Routes

| URL | Route | Notes |
|---|---|---|
| `/{locale}/blog` | `app/[locale]/blog/page.tsx` | page 1; `?category=` and `?page=` 301 to the real URLs |
| `/{locale}/blog/storinka/{n}` | `app/[locale]/blog/storinka/[n]/` | pages 2+, self-canonical, `rel=prev/next` |
| `/{locale}/blog/category/{slug}` | `app/[locale]/blog/category/[slug]/` | indexed, own title/description |
| `/{locale}/blog/category/{slug}/storinka/{n}` | `…/storinka/[n]/` | same, paginated |
| `/{locale}/blog/{slug}` | `app/[locale]/blog/[slug]/` | the article |
| `/{locale}/blog/tag/{tag}` | `app/[locale]/blog/tag/[tag]/` | thin, `noindex`, linked `rel=nofollow` |
| `/api/og/blog/{slug}` | Satori 1200×630 | cover + title + brand |
| `/blog-sitemap.xml`, `/sitemap-index.xml`, `/llms.txt` | routes, not files | see below |

All four list routes render through `components/blog/BlogIndex.tsx`. The list used to exist twice and the copies had already drifted — same failure mode as the editor's photo toolbar.

**Pagination is real URLs, not `?page=`.** `robots.txt` disallows the query form on `/blog` (it duplicates the category pages), so while pagination lived there, every page but the first was closed to crawling. `lib/blog/pagination.ts` owns the URL shape; each page is self-canonical, because a canonical pointing at page 1 drops the articles only visible deeper.

**`/llms.txt` is a route now**, not `public/llms.txt`. The article list in it has to refresh itself, and a static file in `public/` shadows a route at the same path. The unchanging prose lives in `lib/seo/llms-static.ts` (and `tests/partner-rate-wording.test.ts` checks the commission wording there).

### Article page SEO

Everything a search engine sees is built from the row, never written into the body: an editor-typed price or date goes stale silently. `lib/blog/post.ts` computes the meta title (≤60, word-boundary, brand suffix stripped once) and description (140–160, topped up from the body when the excerpt is short).

**hreflang lists only the locales that exist.** `postLocales()` counts the base `locale` plus `translations` keys that have BOTH a title and a body — an empty translation object is created the moment someone opens a language tab — and `getSubsetAlternates()` in `lib/seo/locales.ts` renders that subset. The full five-locale set would tell Google that `/de/blog/…` is a German version of Ukrainian text.

**Known limit — the OG image is not cached at the edge.** `/api/og/blog/[slug]` answers `public, max-age=86400`, so browsers hold it for a day, but `s-maxage` is stripped somewhere in the Next/Vercel layer and `x-vercel-cache` reads `MISS` on every request. Three ways of setting the header (route `revalidate`, `ImageResponse`'s `headers`, a hand-built `Response`) all produced the same result on 2026-09-22 — don't spend a fourth. If edge rendering ever becomes a real cost, render the PNG once when the cron publishes the article and store it, rather than fighting the header.

Structured data: `Article` (author and publisher both the `touch.memories` Organization — no invented human byline), `BreadcrumbList`, `FAQPage` built from the same `faq` rows the accordion renders, and `ItemList` for the product cards. Schema must never promise a question the page does not show.

The minimum internal linking (3 catalog, 2 articles) is held by the page itself, not by the author: product cards give up to three catalog links, "Читайте також" three articles, breadcrumbs one category.

Drafts and queued posts are viewable at `?preview=$BLOG_PREVIEW_SECRET` — `noindex`, no view counted, read through `lib/blog/queue.ts` like every other past-the-gate read.

### Writing articles

`npm run blog:generate -- --list` shows the topic registry; `npm run blog:generate -- <topic-id>` writes one article and queues it (`--dry` prints it without touching the database). **One command, one article, on purpose** — twelve generated at once is twelve nobody re-reads. It runs on plain node (`--experimental-strip-types`), so it imports only files with no path aliases; `ANTHROPIC_API_KEY` is read from `.env.local` and is deliberately **not** set on Vercel, because nothing in production generates articles.

`lib/blog/topics.ts` is the registry. Each topic carries the target page the article links to and an `independent` flag (product mentioned only at the end, never in the title) — the two things the model must not invent, since a made-up catalog slug reads as a working link right up to the click. A topic with no live page carries `blocked` and a reason instead of being quietly pointed at a neighbour.

Nothing is trusted on the model's word:

- every target is checked against the database first — active product, category with products (an empty one 301s to `/catalog`), enabled landing;
- `lib/blog/article-check.ts` then checks the article: 1200–1800 words, 5–8 H2, 3–5 whole FAQ entries, meta lengths, a Latin slug, the key query inside the first hundred words, at least three catalog links and two blog links, no banned mentions, and **no price anywhere** — a price written into prose goes stale in silence and is discovered in the cart. It has no imports (the script loads it under plain node) and `tests/blog-article-check.test.ts` covers it, because a check nobody checks eventually passes everything.

Scheduling is `slotAfterQueue()` in `lib/blog/schedule.ts` — a pure function, so the cron, the admin and this script all compute the same queue instead of each holding a copy.

## SEO surface (canonicals, redirects, sitemap, structured data)

Updated 2026-09-17, after the September audit.

### The four canonical page types

| URL | Route | Structured data |
|---|---|---|
| `/{locale}/catalog/{slug}` | `app/[locale]/catalog/[slug]/page.tsx` | `Product` (+`AggregateOffer` when configurable, `AggregateRating`/`Review` when real reviews exist), `BreadcrumbList`, `FAQPage` when the product has FAQ |
| `/{locale}/category/{ua-slug}` | `app/[locale]/category/[slug]/page.tsx` | `CollectionPage`, `BreadcrumbList`, `ItemList` |
| `/{locale}/category/{ua-slug}/{occasion}` | `app/[locale]/category/[slug]/[occasion]/page.tsx` | same, plus `FAQPage`; content is DB-driven from `landing_pages` |
| `/{locale}/blog/{slug}` | `app/[locale]/blog/[slug]/` | `Article`, `BreadcrumbList`, `FAQPage`, `ItemList` — see "Blog" above |

Every one of them sets a self-referencing canonical and the full five-locale `hreflang` set via `getCanonicalUrl` / `getAlternateLanguages` in `lib/seo/locales.ts`. A page that exists in one language only uses `getSingleLocaleAlternates` instead — do not give it the full set, or we tell Google that five URLs with identical Ukrainian text are five translations.

### Category slugs have two forms, and that is the usual source of redirect bugs

`categories.slug` in the DB is the functional key (`photobooks`), used in 40+ places. The **public** slug is the Ukrainian keyword one (`fotoknygy`), and `lib/seo/categorySlugs.ts` maps between them. The `/category` route resolves the UA slug to the DB row, and answers a DB-slug URL with its own `permanentRedirect` to the UA slug.

That page-level redirect is the trap: **any redirect in `next.config.ts` must point at the PUBLIC UA slug**, never at the DB slug — otherwise it is a two-hop chain, and if the rule happens to point the other way it is an infinite loop. Both existed until 2026-09-17 (`/category/vypuskni-knyhy` ↔ `/category/graduation-books` looped; ~20 rules chained).

### Redirects

All in `next.config.ts` → `redirects()`; `proxy.ts` only adds the locale prefix. Rules that matter:

- **Order is everything.** Next.js applies the first matching rule. A blanket `/shop/:path*` sat near the top of the array and silently swallowed the entire ~60-row `/shop/ → /catalog/` mapping table 200 lines below it, so every old ranking URL landed on the generic catalog. The catch-all now lives at the very bottom, and the comment there says why nothing broad may go above it.
- **Destinations carry `/uk`.** `proxy.ts` answers a locale-less path with another redirect, so `/about → /` → `/uk` was two hops.
- **Query-param rules forward the query.** Next.js copies params the destination does not consume, so a rule whose destination equals its own source loops forever. This is how `/blog?category=…` → `/blog` became an infinite redirect.
- **Check before committing:** `node scripts/redirect-chains.mjs` parses the rules, models both the query forwarding and the category page's own runtime redirect, and exits 1 on any chain, loop, or locale-less destination.

### Sitemap

There are two maps and an index. `app/sitemap.ts` holds the catalog, categories, landings and photographers (~785 URLs, hourly); `app/blog-sitemap.xml/route.ts` holds the articles and blog categories, with a real `lastmod` and a per-row `hreflang` set (hand-written XML, because `MetadataRoute.Sitemap` can only apply one alternates set to every row); `app/sitemap-index.xml/route.ts` lists both. `robots.txt` names all three — a robot is not obliged to expand an index, and a silently unexpanded one would read as a site with no blog.

`app/sitemap.ts`, ~785 URLs, regenerated hourly. It lists only canonical `/catalog/` and `/category/` URLs — **no `/shop/` has ever been in it**, and nothing in it may answer with a redirect. Two rules that already bit us: categories with zero active products are skipped (the page 301s them to `/catalog`), and category paths go through `toPublicCategorySlug`. When adding a redirect for a `/catalog/{slug}` that belongs to an **active** product, check the sitemap — `guestbook-kids` spent months being listed in the sitemap while answering 301.

### Product FAQ

`products.faq` is `jsonb`, an array of `{q, a}`, with translations in `translations.{locale}.faq` — the same convention `landing_pages` uses. `components/seo/ProductFaq.tsx` renders it, and `catalog/[slug]/page.tsx` emits the matching `FAQPage` schema from the same rows, so the markup can never promise a question the page does not show.

Because `ProductClient` owns `<main>` and `<Footer>`, the FAQ is passed into it as `children` rather than appended after it — otherwise it renders below the footer.

There is **no admin UI for product FAQ yet**; edit it in SQL. The admin PATCH route (`app/api/admin/products/[id]/route.ts`) uses a field allowlist that does not include `faq`, so panel edits cannot wipe it.

### Internal linking

`components/seo/LandingLinks.tsx` on the homepage links every active `landing_pages` row plus a short curated list of product pages from `lib/seo/keyPages.ts`. The curated list exists because anchor text is a ranking signal and a catalog card's anchor is the product *name* ("Полароїд"), not the query ("друк фото полароїд"). Keep that list short — if it grows into the whole catalog, every link weighs the same and the point is lost. Slugs are checked against active products at render time, so a renamed product drops out instead of becoming a link to a 404.

## Data model — key tables

(Authoritative shapes are in `lib/supabase/schema/*.sql` and `supabase/migrations/`. This list is for orientation only.)

- **`products`** — catalog items, has `translations` JSONB. Variants and options live INLINE in `products.variants` / `products.options` JSONB columns, not in separate tables.
- **`categories`** — has `translations` JSONB
- **`orders`** — order header. Line items live in `orders.items` JSONB (there is no `order_items` table). Customer info has two paths: linked via `customer_id` → `customers` table, or inline `customer_name` / `customer_email` / `customer_phone` for guest checkout. Designer service info: `with_designer`, `designer_service_fee`, `designer_id`, `brief_token`. **Who is responsible is `manager_id`** (uuid → `staff`), NOT a second `assigned_to` field — a 2026-09-13 audit found `manager_id` already had dropdowns in both the list and the card, a filter of its own, and was set on ZERO of 1092 orders, so a parallel column would have been a second name for an empty thing. A voluntary dropdown had already failed, so the field is now filled as a SIDE EFFECT of `logOutgoingEmail()`: whoever first writes to the customer becomes responsible, and an already-set value is never overwritten (the guard is in the UPDATE's WHERE, so a race cannot beat it). The dropdown stays, now for HANDING OVER rather than first assignment. Mirrored KeyCRM orders get theirs the other way, because the site never mails those customers: `keycrm-mirror` matches `custom_attributes.keycrm.manager_name` against `staff.name` (case- and whitespace-insensitive, EXACT otherwise — «Марія М» in the CRM resembles «Марія Машталір» in the directory just enough to guess wrong, and a wrong assignment looks like a fact) and fills the blank under the same `.is('manager_id', null)` WHERE guard. A name with no staff row assigns nobody and is counted in the mirror report's `manager_unmatched` so the directory can be fixed; two staff sharing one name make the match ambiguous and it is skipped. On 2026-09-13 that matched 636 of 880 mirrored orders, and 237 of the 237 inside the mirror's 14-day window. There is no auto-assignment anywhere else and no escalation. Payment: `monobank_invoice_id`, `monobank_payment_url`, `monobank_invoice_status`, `monobank_approval_code`, `monobank_rrn`, `payment_region`, `paid_at`, `payment_status`, `paid_amount`. **`paid_amount` (added 2026-09-13) is the money actually received** and the only field the admin's payment badge reads. Do not reach for `prepaid_amount` instead: on site orders it is the PLANNED prepayment, written when the Monobank invoice is created and before the customer has paid anything, while on mirrored KeyCRM orders it is a real receipt (`payments_total`). That split is why a partial payment could not be displayed at all before. `payment_status` still holds only `paid`/`pending` (plus `failed`/`refunded`/`cancelled` from the webhook and the unpaid-orders cron), and on a 50/50 order `paid` means the PREPAYMENT cleared, never the order. The badge rule is `lib/orders/payment-state.ts` (pure, tested in `tests/order-payment-state.test.ts`); the CRM bridge keeps its own older reading in `lib/automation/keycrm-money.ts`, which has not yet been moved onto `paid_amount`. **Reporting reads money through `receivedAmount()` / `outstandingAmount()` in that same file (2026-09-14) — never `total`, and never gated on `payment_status`.** Four reports used to compute revenue themselves, all with the same pair of mistakes: `if (payment_status === 'paid') sum += total`. Mirrored KeyCRM orders are paid in instalments and honestly sit at `pending`, so that gate hid every hryvnia already received from them; and on the orders it did let through it counted the ORDER's value rather than the payment's, so an underpaid order scored in full. Moving all four onto `receivedAmount()` on 2026-09-14 moved the numbers like this: the payments page and the expenses P&L both gained **+67,557.73 ₴** on the current month (−3,916.27 correction on already-`paid` orders, +71,474.00 newly visible), client `total_spent` gained **+122,445.84 ₴** all-time (−13,912.65 / +136,358.49), and photographer `orders_total` *fell* **−1,132.00 ₴** — no photographer has a part-paid mirrored order, so that figure is pure correction of money never actually received. The all-time pool of previously hidden money was 281,341.49 ₴; it does not show up whole in any single report because the month views only see September, and `total_spent` only counts orders carrying a `customer_id` or `customer_email` (144,983.00 ₴ of it sits on 178 mirrored orders that carry neither). That pool is also a MOVING number — the KeyCRM mirror re-syncs `paid_amount` continuously, and it shifted from 281,670.49 to 281,341.49 within two hours on 2026-09-14 — so any before/after reconciliation has to be taken from one snapshot. The payments page's «очікує» tile now sums the OUTSTANDING remainder rather than each order's full value: counting a part-paid order's whole total there billed the same money twice, once as revenue and once as awaited (692,148.38 → 345,691.25 ₴). Frozen pricing context (added 2026-06-04): `ship_region` ('UA'|'INTL'), `price_multiplier` (1.0 base, 1.30 intl), `display_currency`, `exchange_rate` (UAH-per-EUR snapshot; null for UAH orders). Two old aliases `mono_invoice_id` / `mono_payment_id` are present but no longer read by any runtime code.
- **`order_history`** — audit trail of order lifecycle events (payment status changes, status transitions, TTN creation, manager/designer assignment). Written by Monobank webhook, automation routes, admin order page. `added_by` now carries the acting staff member on the admin PATCH path (`resolveActingStaff()`); it was NULL on all 655 status and payment rows before 2026-09-13, so «who cancelled this order» had never once been answerable. Empty still means a cron did it. **The cancellation REASON (added 2026-09-13) is a row of its own** with `action = 'order_cancelled'`, separate from the machine-readable «Зміна статусу: new → cancelled» row that other code reads: `details` carries `{reason, note, source, by}` and `notes` the same thing in words. The vocabulary and the row builder live in `lib/orders/cancellation.ts` (pure, tested in `tests/order-cancellation.test.ts`) — seven reasons a person can pick, «клієнт не відповідає» deliberately first and separate because it is the common case, free text mandatory ONLY for «інша причина» (demanding a description where the choice already said everything teaches the team to type a full stop). Customer-side cancellation needs none of this: there is no path by which a customer can cancel their own order.

- **`reviews`** — Instagram imports + manual entries for storefront social proof
- **`design_briefs`** — designer-service customer brief (token-keyed, capability-based access; schema mirrors `lib/types/designer-service.ts`). Token generated server-side by `gen_brief_token()` Postgres function (32-char base64url).

Same migration adds `orders.referral_partner_id` (no FK — `orders` is the most-embedded table in the project and every new key is another chance for gotcha 12) and `agency_commissions.kind`.
- **`partnership_requests`** (applications from the public `/partnery/apply` form; `?kind=blogger|agency` on that URL only preselects the toggle, and the chosen `kind` becomes `agency_partners.partner_kind` on approval) + **`partner_activation_requests`** (a sales manager asking to enrol their own lead, migration `20260806_partner_activation_requests.sql`). Two separate queues into the same partner table, approved by two different routes — `/api/admin/agency-partners` and `/api/admin/partner-requests` — both of which create the partner through `lib/agency/create-partner.ts`.
- **`notification_log`** — outbound Telegram + email status-change notifications, audit only
- **`email_logs`** — the outgoing-mail log for everything the shop sends a customer, surfaced as the «Листування з клієнтом» card on the order page. Brevo is the only transport (`lib/email/resend.ts` keeps the old Resend export names but sends through Brevo). **Write to it only through `logOutgoingEmail()` in `lib/email/log-outgoing.ts`** — never with a hand-rolled insert. That function has a SIDE EFFECT beyond logging, and its name is narrower than what it does: it also sets `orders.manager_id` when the order has none, so a manager is assigned from any of the five send paths at once. Deliberate trade-off, documented in the function's own header; a failed send assigns too, because the person took the order on either way. The insert used to be written out in four places and they drifted: two recorded `body`, none recorded `provider_message_id` (0 of 255 rows), and the «замовлення прийнято» mail from `create-invoice` went through a `.catch(() => {})` that made a provider refusal invisible in both the log and the UI. The helper always writes a row — on success AND on failure — and `readSendOutcome()` normalises the two different result shapes the transports return (`sendEmail` gives `{success,data,error}`, `getResendClient().emails.send()` gives `{data,error}`), which is where the message id kept getting lost. Columns: `order_id`, `customer_email`, `template`, `subject`, `body` (plain-text snapshot — template mails are stripped to text by `htmlToTextSnapshot()` because the card renders it as text), `provider_message_id`, `status`, `error`, `sent_at`, plus `sent_by` → `staff(id)` and `sent_by_name` (added 2026-09-13). `sent_by_name` duplicates the staff name ON PURPOSE, so the log stays readable after a staff row is deleted; both being NULL means the send was automatic (webhook, cron, customer-side checkout). **Delivery (added 2026-09-13):** `delivery_status` / `delivery_detail` / `delivered_at` / `delivery_updated_at` carry what Brevo reports AFTER hand-off, fed by `POST /api/webhooks/brevo`; `failure_kind` (`quota`|`provider`|`config`|`precheck`) says why a hand-off failed, so an exhausted daily cap reads as its own cause rather than a generic error. `delivery_status` is deliberately NOT more values on `status`: `status` answers «did we hand it over» (sent/failed) and `delivery_status` answers «what happened next», and merging them would force a mail we handed over successfully but Brevo could not deliver to read as our own failure. Event freshness is decided by the `ts` INSIDE the event, never by arrival time — Brevo does not guarantee order and a deferred can land after a delivered — and the rule lives in `lib/email/delivery-events.ts` (pure, tested in `tests/email-delivery.test.ts`) alongside the event map, the message-id normaliser (both sides are stripped of angle brackets and lowercased, or matching fails silently) and `describeMailRow()` which the order card renders. The webhook needs `BREVO_WEBHOOK_SECRET` in the `x-webhook-secret` header — Brevo does not sign webhooks, unlike Monobank — answers 503 without it, replies 202 BEFORE doing the work via `after()` from next/server (a floating promise does not survive on Vercel), and treats an unknown event type as a logged 2xx rather than an error. Campaign mail is NOT covered: `email_campaign_queue` stores no provider message id and the drain writes no `email_logs` row, so delivery statuses today cover per-order mail only. **Duplicate suppression (added 2026-09-13) lives in `/api/email/transactional`, not in its callers.** Four paths confirm one payment — the Monobank webhook, check-payment, «Позначити оплаченим» and admin order creation — and each patched separately would see only itself, which is exactly how two identical «оплату отримано» letters reached a customer. They all funnel through this one route, so the rule sits there: if `email_logs` already holds a row for this `order_id` + `template` with `status='sent'` inside `DUPLICATE_WINDOW_HOURS` (24, a constant in `lib/email/log-outgoing.ts`), the send is skipped and the route answers 200 with `skipped: true, duplicate: true` — an error would only make Monobank retry the webhook forever. It checks the FACT of a successful send, so a failed attempt never blocks a retry, and a failure to read the log lets the mail through (silence about a received payment is worse than a second letter). Guarded actions are `paid` and `shipped`, which describe events that happen once; `placed` is deliberately exempt because the «Надіслати посилання клієнту» button re-sends it on purpose. Pure parts tested in `tests/email-duplicates.test.ts`. **The address a customer is told to write to is `SHOP_CONTACT_EMAIL` in `lib/email/contact-address.ts`, never a literal.** It is NOT the sender address: mail goes out from `hello@touchmemories.com.ua`, whose domain is verified in Brevo so sending works and everything looks fine, while no mailbox exists behind it at all. Six templates — AbandonedCart, OrderCancelled, PaymentReminder, ReviewRequest, WelcomeSeries, WinBack — invited the customer to write to exactly that dead address; they were moved onto the constant on 2026-09-13 and `tests/email-duplicates.test.ts` fails if the string comes back in any template. In the three marketing ones (AbandonedCart, WelcomeSeries, WinBack) that invitation was worded as the unsubscribe instruction, and an earlier draft of this file read that as leaving people with no way out of the mailing list. **That was wrong, and the correction matters because it changes what the defect was.** Marketing mail already carries a working «Відписатися від розсилки» link plus `List-Unsubscribe` / one-click headers, both added by `withUnsubscribeFooter()` in `lib/email/unsubscribe.ts` whenever the caller passes `unsubscribe` — and the abandoned-cart, win-back and welcome-series crons all do. What the dead address really created was a SECOND, competing route out that happened to be broken: a reader who followed the body text instead of the footer wrote to a mailbox that does not exist, got no answer, and stayed subscribed. So the fix was not to re-point that sentence at a live address but to delete it, which was done on 2026-09-13 — the footer is the single way out, and `tests/email-duplicates.test.ts` now fails if the text instruction reappears in any of the three. **Do not add an unsubscribe instruction to an email body: the footer already is one.** `emails/DesignerBriefEmail.tsx` still prints `info@touchmemories.com.ua`, a third address nobody has confirmed is alive. The acting person is resolved by `resolveActingStaff()` in `lib/auth/guards.ts` — `staff` has no auth-user column, it is matched by email — and is passed in the request body to `/api/email/transactional`, which is called server-to-server with the cron secret and so never sees the manager's cookies.
- **Guest orders are linked to accounts at REGISTRATION, and only on positive proof of identity (2026-09-14).** `orders.customer_id` used to be written in exactly one place — `/api/orders/submit`, and only when a session existed at checkout. No session meant the field stayed empty forever; nothing anywhere back-linked, and the registration route never touched `orders` at all. By 2026-09-14 that left 64 registered customers with an empty card despite 69 510 ₴ of purchases, plus 2 with a split history. The cause was NOT «bought before registering»: **71 of those 72 orders were placed AFTER registration**, on average 3.2 days later — people who have an account simply check out logged out, and guest checkout is the norm rather than the exception (only ~40% of site orders carry a `customer_id`, steady across July–September). `linkGuestOrdersForCustomer()` in `lib/customers/link-guest-orders.ts` runs over every guest order with the same normalised email, **from `app/[locale]/auth/callback/route.ts` — not from `/api/auth/register`, which nothing called and which is deleted as of 2026-09-14**. That is where it was first put, and it never ran once: both signup forms go straight to `supabase.auth.signUp` and the customer row is created by the `handle_new_auth_user` trigger on `auth.users`, so the route is dead code. It is also broken independently — its `customers` insert names `birthday_day` / `birthday_month` / `birthday_year`, three columns that do not exist, and its failure path deletes the auth user it just created; 35 people entered a birthday at signup and only 5 have one in `customers`, because that route was the only thing that ever wrote it. The linking does NOT live in a DB trigger either: the matching rule is TypeScript with tests over real pairs, and a PL/pgSQL twin would be a second copy of the rule — the same trap the paid-in-full rule fell into. The auth callback is the one server-side point every signup passes through, email confirmation and Google alike, so it does not depend on whoever writes the next login form remembering to call anything. **Matching on email alone is not safe and the data proves it**: one address is shared by a family, and the account «Svitlana Krasnova» is used repeatedly to order for «Ірина Байдакова», while «Julia Savkiv» carried orders for «Савків Наталія» — same surname, different person. So the decision belongs to `lib/customers/name-match.ts` (pure, tested in `tests/customer-name-match.test.ts` against 50 REAL pairs from the base, which is how two wrong versions of the rule were caught). It folds ru/uk letter variants and apostrophes, transliterates Cyrillic to Latin, and then requires **two matching name tokens** when both names have two or more — one shared surname is not enough, which is exactly what stops the Savkiv case. A differing phone can only ever force a review, never permit a link. There is deliberately **no list of diminutives**: «саша»/«Олександра» and «Ліза»/«Єлизавета» go to manual review like everything else, because such a list needs endless upkeep and the first missing pair becomes either a wrong link or an inexplicable exception (Diana, 2026-09-14). On the 50 real pairs the rule links 16 and sends 34 to review, with no wrong link among them. Everything it will not link is parked on `orders.link_candidate_customer_id` / `link_candidate_at` / `link_candidate_reason` (migration `20260914_order_link_review.sql`) and **shown as a list at the top of the admin «Клієнти» page**, served by `/api/admin/clients/link-review` — a flag without a visible list just accumulates, which is precisely how those 79 orders accumulated in the first place. A manager's «ні, різні» writes `link_review_rejected_at` so the pair never returns. Mirrored KeyCRM orders are skipped entirely.
- **`order_last_contact`** (VIEW, added 2026-09-13) — `order_id`, `last_contact_at`, `letters_sent`, aggregated from `email_logs`. Every other filter in the orders list runs in the browser over the 200 newest rows already fetched, which is exactly the page a stuck order has fallen off; the same approach here would show an empty list precisely when it is needed. ### Session start protocol (when collaborating with Antigravity)
Antigravity often pushes to the same repo concurrently. Always start with:
```bash
git fetch origin && git reset --hard origin/main
```
After making changes, before pushing, rebase and check for conflicts. If Antigravity already applied something similar, cherry-pick only the new commits.

### Patch protocol
Use `str_replace` for code patches, **not** `git apply`. The `git apply` workflow has caused issues in past sessions.

### TypeScript check
```bash
npx tsc --noEmit | grep error TS | grep -v TS2307
```
The `-v TS2307` filter intentionally hides module-not-found errors that are not relevant to current changes.

    - `20260429_security_hardening.sql` — enable RLS on `magazine_briefs` (was off; PII questionnaires were anon-readable), drop public SELECT on `subscribers` / `wishlists` / `gift_certificates` / `inventory_movements`, drop `Free Designer Orders Read` (anon-leaked customer PII for designer-service orders), drop anon FOR ALL on `photobook_projects` / `recipes`, restrict `bank_accounts` / `fiscal_accounts` / `np_accounts` to admin only, drop `staff` "any authenticated reads" policy, drop `design_briefs` / `design_revisions` `USING (true)` policies, lock down orphan tables from sibling projects.
    - `20260429_security_hardening_admin_check_fix.sql` — fixes the previous migration's admin check. The first attempt used `EXISTS (admin_users WHERE id = auth.uid())` but `admin_users.id` is its own UUID, NOT `auth.users.id`. Replaced with the existing `is_admin()` DB function (matches via `auth.jwt()->>'email'`).
    - `20260429_close_customer_projects.sql` — `customer_projects` had a policy literally named "Admin full access" but with `USING (true)` and no role restriction; full table was anon-readable. Closed with admin/owner policies; the customer review link path now goes through `/api/review/[token]/[action]` with token-validated service-role access.

    Code-side fixes:
    - `lib/auth/guards.ts` — new `requireAuth` / `requireAdmin` / `requireOwnerOrAdmin` helpers for API routes.
    - 24 `/api/admin/*` routes — added `requireAdmin()` at the top of every handler. Previously they used the service-role client with no auth check; anyone could GET/PATCH any order, change `payment_status`, etc.

14. **Dashboard and analytics still report `total`, not money received** (open, 2026-09-14 — deliberately NOT part of the four-consumer fix in `1513a701`). `/api/admin/dashboard` computes `todayRevenue` as the sum of `total` over every order created today regardless of payment, and `awaitingPaymentSum` as the sum of `total` where `payment_status = 'pending'` — the full order value, not the outstanding balance. `/api/admin/analytics` reads `total` for revenue, the period-over-period change, the 30-day chart and the COGS match. So both pages answer «how much was ordered», while the payments page, client `total_spent`, the expenses P&L and photographer totals now answer «how much came in», and the two sets of numbers disagree on every partially-paid order. Moving them over means `receivedAmount()` in the routes AND the `get_daily_revenue` SQL function, which is a second copy of the rule living in the database — change one without the other and the 30-day chart silently keeps the old answer.
